# Code-Bereich

> Ein Modul als Code gelesen: seine Funktionen, das ASM-Listing, der dekompilierte C und die Bytes, auf die eine Instruktion zeigt.

**Mit Code öffnen** im Baum [[topic:tool-uefi|UEFI-Struktur]] öffnet ein Modul, für das der Speicher eine Analyse hält: die Bytes des Moduls und der Code nebeneinander in einem Fragment-Bereich, benannt nach dem Modul und dem Format des Abbilds, etwa `SecCore ▸ PE32`. Die Analyse ist schreibgeschützt — Änderungen gehören in den Dump —, und der Bereich ist der Ort, an dem sie gelesen wird: die Funktionen links, das ASM-Listing oder der C der gewählten Funktion oben, die Bytes des Moduls unten.

## Der Code

Der Code wird gelesen, nicht bearbeitet, daher hat der C-Code keine Einfügemarke. Stattdessen ist die zuletzt angeklickte Zeile mit einem hellen Band über die ganze Breite des Codes markiert, wie ein Editor die aktuelle Zeile markiert. Das Band ist durchscheinend, sodass die Farben eines Vergleichs darunter sichtbar bleiben, und es wird ausgeblendet, solange ein Textblock ausgewählt ist; **↑** und **↓** bewegen sie um eine Zeile, **Bild auf** und **Bild ab** um eine Bildschirmseite, **Pos1** und **Ende** zur ersten und zur letzten Zeile, und der Code rollt so, dass sie sichtbar bleibt. Im ASM-Listing ist die ausgewählte Anweisung mit demselben Band markiert, und dieselben Tasten bewegen sie.

Im Code-Bereich führt der Code dorthin, was er nennt. Ein Klick auf einen Namen hebt jede Stelle hervor, an der er vorkommt: einen Parameter oder eine lokale Variable in der gezeigten Funktion, eine Funktion oder eine globale Variable im C und im ASM-Listing überall dort, wo dieselbe Adresse genannt ist. Ein Klick auf etwas anderes oder **Esc** hebt die Hervorhebung auf. **⌘**-Klick oder Doppelklick auf einen Parameter oder eine lokale Variable wählt die Stelle aus, an der sie definiert ist: den Parameter in der Signatur der Funktion, die lokale Variable in den Deklarationen am Anfang der Funktion. Der Name einer aufgerufenen Funktion ist im C wie im ASM-Listing ein Link, der unter dem Zeiger unterstrichen wird: **⌘**-Klick oder Doppelklick öffnet diese Funktion, und ihre Bytes werden zur Hauptzone des Dumps. Ebenso wählt ein Sprungziel die Instruktion aus, auf der der Sprung landet; die Bytes einer globalen Variablen oder einer GUID wählt ein **⌘**-Klick, denn ein Doppelklick auf einen solchen Namen fragt, was er ist. Die Sprungmarke eines `goto` ist ebenso ein Link: Ein Klick mit **⌘** oder ein Doppelklick wählt die Zeile im C aus, in der die Marke definiert ist, und, solange ihr Name noch die Adresse nennt, auch ihre Anweisung; ein einfacher Klick hebt die Marke überall hervor, wo sie genannt ist. Ein Sprung zu einer Stelle aus der Liste **Verwendet bei** im Popover eines Namens ist ebenfalls eine Bewegung. Solange der Bereich die Tastatur hat oder im Vordergrund liegt, gehen **Darstellung ▸ Zurück** und **Darstellung ▸ Vorwärts** (**⌘[** und **⌘]**) sowie die Schaltflächen **‹ ›** in der Symbolleiste die Stellen zurück und wieder vor, zu denen diese Klicks geführt haben. Über die erste dieser Stellen hinaus führt **Zurück** durch den [[topic:navigation|Verlauf]] des Tabs: Eine Stelle außerhalb des Bereichs klappt den Bereich ein, und **Vorwärts** holt ihn zurück. Eine Stelle wird so wiederhergestellt, wie sie verlassen wurde: ASM-Listing und C sind dorthin gescrollt, wo sie standen, und der Aufruf, dem gefolgt wurde, ist wieder ausgewählt. Eine über einen Link geöffnete Funktion zeigt ihr C von Anfang an. Die Stelle, an der man ankommt — die Zeile der Instruktion im Listing, im C der Aufruf oder der Name der Funktion in ihrer Signatur —, wird kurz hervorgehoben, damit sie leicht zu finden ist.

Solange ein Name hervorgehoben ist, führen **Bearbeiten ▸ Nächstes suchen** (**⌘G**) und **Bearbeiten ▸ Vorheriges suchen** (**⇧⌘G**) von einer Stelle, an der er vorkommt, zur nächsten — im C oder im ASM-Listing, je nachdem, was gezeigt wird: Die Stelle wird ausgewählt, in den sichtbaren Bereich gebracht und kurz markiert. Der Zähler neben **ASM** und **C** gibt an, wie viele Stellen es gibt und bei welcher man ist — der angeklickten oder der zuletzt angesprungenen; seine beiden Pfeile tun dasselbe wie die Tasten. Nach der letzten Stelle geht es reihum zur ersten, und der Bereich zeigt dasselbe Zeichen wie eine Suche, die von vorn beginnt. Ist nichts hervorgehoben, suchen die Tasten wie gewohnt im Dump.

## Namen, die sich selbst erklären

Ein Name, den die Analyse einer Konstante gegeben hat — einem I/O-Port wie `PCI_CONFIG_ADDRESS`, einem MSR, einem Bit eines Chipsatz-Registers —, ein Typ wie eine Struktur und ein Feld einer Struktur erklären sich selbst: Ein Klick darauf öffnet daneben ein Popover. Für eine Konstante zeigt es die Zahl hexadezimal und dezimal, die Gruppe von Namen, zu der sie gehört (etwa `FCH_IO_PORT`), wofür der Name steht, und die Instruktionen, die sie verwenden — ein Klick auf eine davon führt dorthin —, sowie ganz am Ende in kleinerer Schrift die Quelle, aus der diese Angabe stammt. Für einen Typ zeigt es seine Definition mit Offset und Kommentar jedes Felds, für ein Feld dieselbe Definition mit hervorgehobener Zeile des Felds. Auch eine benannte globale Variable des Moduls, etwa `mPciExpressBaseAddress`, öffnet das Popover: ihr Typ und ihre Adresse, der Wert, den das Image dort hält, der Kommentar der Analyse dazu und die Instruktionen, die sie lesen oder schreiben. **⌘**-Klick darauf markiert ihre Bytes im Dump, so viele, wie ihr Typ einnimmt; ein Klick und ein Doppelklick öffnen das Popover. Eine Zahl im ASM-Listing, der die Analyse einen Namen gegeben hat, öffnet dasselbe Popover. Hat die Analyse einen Namen noch nicht erklärt, sagt das Popover dies und zeigt nur die Fakten: den Wert und die Definition des Typs.

Ein Klick auf den Aufruf einer Funktion öffnet daneben ein Popover mit dem Analysezeichen vor dem Namen der Funktion, ihrer wie der Code eingefärbten Signatur, dem ersten Absatz des Kommentars darüber, der den Zweck der Funktion nennt, und **Zur Funktion**. Im Vergleich wirkt derselbe Klick ebenso. **⌘**-Klick und Doppelklick gehen sofort zur Funktion, ohne Popover.

Lässt der Decompiler von Ghidra Blöcke aus dem C weg, weil bei den ihm bekannten Werten kein Pfad sie ausführt, sagt das C dies in einer Zeile: `/* WARNING: Removing 74 unreachable blocks */`. Ein Klick auf die Zeile öffnet die Liste der Adressen der entfernten Blöcke; ein Klick auf eine Adresse führt zu den Instruktionen des Blocks im Listing, wo sie alle erhalten sind. Meist ist ein solcher Block Code, den dieser Firmware-Build nie ausführt, etwa ein Zweig für eine andere Einstellung als die dieser Platine. Ein Block, der von der Antwort der Hardware abhängt, kann auf der Platine dennoch ausgeführt werden: eine Prüfung, die im Modell von Ghidra nicht fehlschlagen kann, etwa der Test, ob der Speicher den hineingeschriebenen Wert hält.

## Der Kopf

Über der Liste links stehen das Modul und in Klammern die Revision seiner veröffentlichten Analyse — **(r14)**. Die Zeile darunter nennt die Analyse und die Ghidra-Version, mit der sie erstellt wurde. Sind mehrere Analysen des Moduls gespeichert, ist diese Zeile ein Menü: Jede Analyse ist dort gleich benannt, und eine gewählte stellt den Code des Moduls aus dieser Analyse dar und lässt dieselbe Funktion und Instruktion auf dem Bildschirm. Der Kopf über dem Code nennt die gezeigte Funktion mit dem Analysezeichen vor ihrem Namen. Der Name des Moduls und der Name der Funktion lassen sich markieren und kopieren. Der Zeiger über dem Zeichen nennt die Stufe und was fehlt, bei einer Bibliotheksfunktion die Angaben des Registers. Der eigene Name der Funktion in ihrer Signatur ist kein Link: Diese Funktion ist bereits geöffnet. Wird sie aufgerufen, unterstreicht sich der Name unter dem Mauszeiger wie ein Aufruf, und ein Klick darauf — ebenso **⌘**-Klick oder Doppelklick — öffnet stattdessen **Aufrufe anzeigen…**. Ein Rechtsklick auf den Namen einer Funktion — im Kopf, in der Signatur oder an einem Aufruf im C — bietet **Aufrufe anzeigen…** an; an einem Aufruf steht davor **Gehe zu Definition**, das wie ein **⌘**-Klick die aufgerufene Funktion öffnet. Die Liste öffnet sich als Popover neben dem Namen und nennt jeden Aufruf dieser Funktion, eine Zeile je Aufruf: die aufrufende Funktion, die Adresse des Aufrufs und ihre Instruktion; ein Sprung, mit dem die aufrufende Funktion endet, ist mit **Sprung** markiert. Eine Funktion, die sie zweimal aufruft, steht zweimal da. Eine aufrufende Funktion, die Ghidra kennt, deren Aufruf im Listing aber nicht gefunden wurde — ein Aufruf über einen Zeiger —, steht mit **Aufrufstelle unbekannt** da. Ein Klick auf eine Zeile schließt das Popover und öffnet die aufrufende Funktion an diesem Aufruf, markiert im Listing und im C; eine lange Liste lässt sich im Popover scrollen.

Werden die Analysen auf einem Analyseserver gehalten, zeigt der Kopf der Liste links direkt nach der Revision den Zustand des Servers. Der Server sendet alle 5 Sekunden ein kurzes Signal, und die App überwacht dessen Eingang. Eine graue Wolke bedeutet, dass das Signal eintrifft. Eine bernsteinfarbene Wolke mit Ausrufezeichen in kräftigen Linien bedeutet, dass sich das Signal um etwa 8 Sekunden verspätet; ein Fehler liegt noch nicht vor. Eine rote Wolke mit Kreuz bedeutet, dass die Verbindung verloren ist: etwa 20 Sekunden kein Signal, kein Netzwerk auf diesem Mac oder ein Server, der nicht antwortet oder das Token dieses Macs ablehnt; den Grund nennt der Hinweis unter dem Mauszeiger. Bereits gelesener Code bleibt lesbar, noch nicht gelesener Code ist erst wieder verfügbar, wenn die Verbindung besteht. Während der Verbindungsaufnahme pulsiert die Wolke. Ein Server einer früheren Version sendet kein Signal: Solange er antwortet, bleibt die Wolke bernsteinfarben, und vom Verbindungsverlust erfährt die App erst beim Fehlschlagen einer Anfrage, was bis zu einer Minute dauern kann. Werden die Analysen auf diesem Mac gehalten, erscheint kein Symbol.

## Beschreibung

**Beschreibung**, die Schaltfläche mit dem Buch rechts neben dem Modulnamen über der Liste, zeigt anstelle des Codes die Beschreibung des Moduls: wozu das Modul dient, wie es arbeitet und wie es aufgebaut ist — seine Schnittstellen, der Ablauf ab dem Einstiegspunkt, die Funktionen nach ihrer Aufgabe, die angesprochene Hardware, die gemeldeten Codes, die Befunde der Analyse und was noch unbekannt ist. Die Beschreibung entsteht bei der Analyse zusammen mit den Namen und Kommentaren und wird mit ihnen in derselben Revision veröffentlicht; sie beschreibt also stets den gezeigten Code. Eine darin genannte Funktion — als Link oder als Code geschrieben — ist ein Link: Ein Klick öffnet die Funktion im Code, und **Darstellung ▸ Zurück** führt an die Stelle der Beschreibung zurück, an der sie verlassen wurde. Auch ein Klick auf eine Funktion in der Liste links führt zum Code zurück. Am Buch ist zu sehen, ob die Analyse bereits eine Beschreibung verfasst hat; solange das nicht der Fall ist, lässt sich nichts öffnen. Ein Modul mit Beschreibung öffnet sich auf ihr: Der Bereich zeigt zuerst die Beschreibung, und zum Code gelangt man mit einem Klick auf das Buch oder auf eine Funktion in der Liste. Ein Bereich, der an einer bestimmten Funktion geöffnet wird — über einen Link oder eine Anmerkung —, zeigt diese Funktion. Was eine Beschreibung feststellt, ist die Lesart des Codes durch die Analyse; Unbewiesenes ist als solches gekennzeichnet.

Dieselbe Schaltfläche blendet sie wieder aus, ebenso die runde Schließen-Schaltfläche in der oberen rechten Ecke der Beschreibung. Solange sie gezeigt wird, erscheint der Umschalter **ASM** und **C** über dem Code nicht und keine Funktion wird genannt, denn sie gilt für das ganze Modul. Eine Spalte links neben der Beschreibung listet ihre Abschnitte wie das Inhaltsverzeichnis der Hilfe auf und folgt dem Lesen; ein Klick auf einen Abschnitt rückt ihn an den oberen Rand der Ansicht. **Darstellung ▸ Zurück** führt an die vorherige Stelle der Beschreibung zurück.

## Diff

Die Leiste unter dem Code trägt den Vergleich, wie in Xcode: diese Revision, die zwei Pfeile, eine Auswahl der Revisionen des Moduls und **Zurücksetzen**. Die Auswahl nennt die Revisionen, deren Code der Speicher hält, die neueste zuerst; eine gewählte Revision macht die C-Seite zum Vergleich der Funktion auf dem Bildschirm mit derselben Funktion in der gewählten Revision, Zeile für Zeile — die alte und die neue Zeilennummer jeder Zeile, das Entfernte rot, das Hinzugekommene grün, die gemeinsamen Zeilen unverändert. Eine Funktion, die die frühere Revision nicht hatte, liest sich als ganz hinzugefügt, und eine, die beide Revisionen gleich halten, steht als Code da, nicht als Diff von nichts. Der Code im Diff ist mit den Tokens des Artefakts gezeichnet, wie der C, und antwortet auf einen Klick wie dieser: ein Name hebt jedes Vorkommen im Diff hervor, **⌘**-Klick folgt einem Aufruf, und ein Name, der sich selbst erklärt, öffnet sein Popover — eine Zeile der früheren Revision aus deren Analyse. Das Listing bleibt das dieser Revision: verglichen werden die C-Seite und die Beschreibung. **Zurücksetzen** oder **Kein Vergleich** in der Auswahl bringt den Code zurück. Der Code einer Revision, der auf diesem Rechner noch nicht vorliegt, wird zuerst vom Analyseserver geladen, und der Vergleich erscheint, sobald er eingetroffen ist; eine neue Wahl in der Zwischenzeit ersetzt die frühere. Lässt sich der Code einer Revision oder einer anderen Analyse nicht lesen, behält der Bereich die aktuelle Anzeige, und der Grund — das Objekt ist beschädigt oder nicht im Speicher vorhanden — bleibt rot im linken Teil der Leiste stehen, bis neu gewählt wird; der Grund für eine Revision erscheint zusammen mit ihrer Funktion. Ein Ausfall der Verbindung zum Server zeigt sich nur an der Wolke im Kopf der Liste. Dauert ein Lesevorgang länger — der Code einer Revision, die Liste der Revisionen des Moduls, eine andere Analyse —, zeigt der linke Teil der Leiste einen Fortschrittsbalken und nennt, was gelesen wird: **geladen**, solange der Code einer Revision vom Analyseserver kommt, **gelesen**, solange dieser Rechner verarbeitet, was er bereits hält. Der Balken zeigt, dass die Arbeit läuft, nicht, wie viel noch aussteht. Empfängt der Bereich eine spätere Revision, vergleicht er sofort mit der vorigen, und das Öffnen einer von ihr geänderten Funktion schaltet diesen Vergleich von selbst ein. Eine Marke behält die früheste Revision, gegen die die Funktion neu war, und das Öffnen vergleicht mit ihr, auch wenn danach weitere Revisionen kamen; solange der Leser auf dieser Funktion bleibt, ändert eine eintreffende Revision den Vergleich nicht. Jede Funktion hat ihren eigenen Vergleich: eine Funktion, die die Revision nicht geändert hat, steht da, wie sie ist, und eine Funktion, deren Marke entfernt wurde, wird bei der Rückkehr weiterhin mit der Revision verglichen, die die Marke gebracht hat, bis eine spätere Revision sie erneut markiert. Eine in der Leiste gewählte Revision und **Zurücksetzen** wirken nur auf die Funktion auf dem Bildschirm. Diese Auswahl gilt, solange der Bereich geöffnet ist, und wird nicht im Arbeitsbereich gespeichert. Die Revision, in der eine Funktion zuletzt gelesen wurde, bleibt mit dem Modul über Neustarts hinweg erhalten; eine Revision, die eingetroffen ist, während die App geschlossen war, kennzeichnet daher die von ihr geänderten Funktionen erneut als **Neu** und vergleicht sie mit der Revision, in der sie zuletzt gelesen wurden. Eine Revision, deren Code der Speicher nicht hält — eine Aufzeichnung aus der Zeit, bevor Revisionen ihren Code behielten —, erscheint in der Auswahl nicht. Von den übrigen bietet die Auswahl nur jene an, die den C-Code der gezeigten Funktion geändert haben und vom Gezeigten abweichen, sodass eine Wahl immer einen Vergleich mit Inhalt ergibt; eine Funktion, die in keiner früheren Revision abweicht, bietet nur **Kein Vergleich**. Eine Revision erscheint außerdem, solange nicht bekannt ist, was sie geändert hat, etwa in einer Aufzeichnung, die der Server noch nicht verarbeitet hat. Eine mit **New** markierte Funktion, deren Änderung nicht im Code liegt — sie wurde umbenannt, ihre Signatur wurde geändert oder die Revision hat sie hinzugefügt —, trägt eine gelbe Plakette über dem Code: das **New**-Zeichen neben einem Titel und eine Aufzählung dessen, was sich außer dem Code geändert hat. Liest sich der Code in beiden Revisionen gleich, sagt die Plakette das, denn der Vergleich hat nichts zu zeichnen. Hat eine Funktion nur im Code eine Änderung, gibt es keine Plakette: der Vergleich ist die Erklärung.

Solange die Beschreibung angezeigt wird, vergleicht dieselbe Leiste die Beschreibung. Die Auswahl bietet die Revisionen an, in denen sie sich geändert hat; die Wahl einer Revision zeigt die Beschreibung in ihrer jetzigen Fassung zusammen mit dem Text der gewählten Revision, so wie der C-Code verglichen wird: was nur die gewählte Revision enthielt, ist rot hinterlegt und mit − gekennzeichnet, was nur diese enthält, grün und mit +. Ist die Beschreibung in beiden Revisionen gleich, wird sie unverändert gezeigt. Die Verweise führen auch im Vergleich zum Code. Die Beschreibung hat einen eigenen Vergleich, getrennt von dem jeder Funktion: die für sie gewählte Revision bleibt erhalten, wenn der Benutzer zum Code wechselt und zurückkehrt, und **Zurücksetzen** wirkt nur auf sie. Liest sich die Beschreibung anders als beim letzten Öffnen durch den Benutzer, steht links neben dem Buch **Neu**; beim Öffnen wird sie mit der Revision verglichen, in der sie zuletzt gelesen wurde, und die Markierung verschwindet, sobald der Benutzer die Beschreibung verlässt — wie bei einer Funktion. **Markierungen „Neu“ entfernen** entfernt sie zusammen mit den Markierungen der Funktionen.

## Suchen im Code

Über einem Code-Bereich öffnet **Bearbeiten ▸ Suchen** (**⌘F**) die Suchleiste oberhalb des Codes statt oberhalb der Bytes des Moduls; gesucht wird dann im Text, und zwar im C der angezeigten Funktion oder, solange sie geöffnet ist, in der Modulbeschreibung. Das ASM-Listing wird nicht durchsucht: Eine Suche, die bei angezeigtem Listing beginnt, schaltet auf das C um. Eine Kodierung ist hier nicht wählbar; wie verglichen wird, bestimmen **Groß-/Kleinschreibung beachten** und **Ganzes Wort**. Mit Letzterem gilt nur ein vollständiger Name als Treffer, nicht ein Teil eines längeren Namens. Alle Treffer werden grau hinterlegt; der aktuelle wird ausgewählt, in den sichtbaren Bereich gebracht und gelb markiert. Die gelbe Markierung bleibt bestehen, bis die Auswahl verschoben wird. **Return**, **‹ ›**, **Nächstes suchen** (**⌘G**) und **Vorheriges suchen** (**⇧⌘G**) springen von Treffer zu Treffer; nach dem letzten beginnt die Suche wieder am Anfang, mit demselben Hinweis wie im Dump. Kommt das Muster nicht vor, meldet dies die Suchleiste, begleitet von einem Signalton. **Auswahl suchen** (**⌘E**) übernimmt den im C oder in der Beschreibung ausgewählten Text. Im Code gefundene Muster werden in einer eigenen Liste **Zuletzt gesucht** geführt, getrennt von der des Dumps.

**Bearbeiten ▸ In allen Funktionen suchen** (**⇧⌘F**) oder die Lupe am Ende des Umschalters über der Liste zeigt an Stelle der Liste den Such-Tab. Er durchsucht in einem Durchgang das C aller Funktionen des Moduls und dessen Beschreibung. Sein Feld enthält dasselbe Muster wie die übrigen Suchfelder des Programms; bei **⇧⌘F** wird der im C ausgewählte Text eingesetzt, ohne Auswahl das zuletzt gesuchte Muster. **Return** startet die Suche; **Groß-/Kleinschreibung beachten** und **Ganzes Wort** wirken wie in der Suchleiste, und das Menü des Felds enthält die letzten Suchanfragen. Unter dem Feld wird der Suchbereich gewählt: **Überall**, **In Funktionen** oder **In der Beschreibung**. Funktionen, deren C der Code-Bereich noch nicht geladen hat, werden zuerst geladen; bei einem großen Modul dauert das einen Moment, was der Tab währenddessen anzeigt. Das Ergebnis erscheint als Baum: jede Funktion mit Treffern, mit ihrem Analysezeichen, oder die Beschreibung, darunter jede Zeile, die das Muster enthält, mit dem Treffer in Fettschrift. Steht ein Treffer weit hinten in einer langen Zeile, wird der Zeilenanfang zu `…` gekürzt. Die Zeile über dem Baum nennt die Zahl der Ergebnisse und der Funktionen. Die Suche endet nach 5000 Ergebnissen und weist darauf hin, dass nur die ersten aufgeführt sind; ein genaueres Muster liefert alle. Ein Klick auf eine Ergebniszeile oder **↑** und **↓** im Baum öffnen die Funktion oder die Beschreibung, wobei die Fundstelle ausgewählt und kurz markiert wird. Solange das Ergebnis angezeigt wird, sind alle Vorkommen seines Musters in der Funktion oder Beschreibung auf dem Bildschirm grau hinterlegt, sofern die Suchleiste über dem Code dort keine eigenen Treffer hat.

## Einen Namen kopieren

Den Namen des Moduls oben im Code-Bereich kann man auswählen und kopieren, ebenso den Namen einer Funktion in der Funktionsliste: mit **Namen kopieren** im Kontextmenü der Zeile oder mit **Bearbeiten ▸ Kopieren** (**⌘C**), solange die Liste die Tastatur hat.

## Die Listen

Der Umschalter über der Liste wählt, was sie enthält: **Funktionen**, **Zeichenketten**, **POST** oder **Status**. Die erste öffnet eine Funktion — ein Klick auf ihren Namen zeigt ihren Code; die übrigen sind Tabellen dessen, was die Analyse gefunden hat.

Die Marke einer Funktion zeigt, wie weit ihre Analyse fortgeschritten ist, gleich an welcher Stelle der Liste — an der Wurzel des Aufrufbaums, unter der aufrufenden Funktion oder in einer Gruppe: ein `f` auf einem Quadrat in der Farbe der Funktionsnamen im Code für eine vollständig analysierte Funktion, dasselbe `f` in einem orangefarbenen Rahmen für eine teilweise analysierte und für eine Bibliotheksfunktion eine blaue Marke mit dem Kurznamen ihrer Bibliothek — **EDK2**, **AMD** oder **Intel**; eine Funktion, bis zu der nur der Dekompiler gekommen ist, trägt dasselbe `f` in einem roten Rahmen, eine Funktion ohne Rumpf dasselbe `f` in einem grauen Rahmen, eine Funktion jeder anderen Stufe das `f` auf dem Quadrat. Die Marke einer Funktion hat die Farbe der Marke ihrer Gruppe. Die Leiste unter der Liste enthält das Filterfeld, das die gezeigte Liste eingrenzt, und, solange **Funktionen** gezeigt wird, drei Schaltflächen, die die Reihenfolge der Funktionen bestimmen. **Nach Adresse** ist eine Tabelle der Funktionen, wie die Analyse sie exportiert hat — zuerst die Adresse, dann der Name —, wo jede Funktion im Modul liegt. **Aufrufbaum** zeigt die gewählte Funktion in ihrem Zusammenhang und lässt die übrigen Funktionen des Moduls weg. Zu sehen sind alle Wege zu dieser Funktion, jeweils ausgehend von einer Funktion, die im Modul niemand aufruft — dem Einstiegspunkt, einem Notify-Callback, einem Platz einer Diensttabelle —, und alle sind geöffnet; unter der Funktion steht der Baum ihrer Aufrufe, wobei die Aufrufe einer Funktion alphabetisch geordnet sind. Wird eine andere Funktion gewählt, entsteht der Baum neu um diese, und alle Wege sind wieder geöffnet. Der Pfeil vor einer Funktion öffnet und schließt, was unter ihr liegt. Kein Weg führt zweimal über dieselbe Funktion: Der Aufruf einer Funktion, die bereits auf dem Weg liegt, also ein rekursiver Aufruf, erscheint mit `↺`, ohne Pfeil, und der Baum endet dort. Ein Aufrufkreis, in den kein Aufruf von außen führt, beginnt bei seiner alphabetisch ersten Funktion. Führen mehrere Wege zur Funktion, steht sie am Ende jedes Weges, und ihre Aufrufe sind nur an einer dieser Stellen geöffnet: dort, wo sie gewählt wurde, sonst an der ersten. Diese Stelle hat den Hintergrund von markiertem Text im Code und steht zusammen mit dem Weg dorthin in Fettschrift; die übrigen Stellen der Funktion stehen in normaler Schrift auf hellgrauem Hintergrund. Ein Klick auf eine solche Stelle verlegt die Aufrufe dorthin und ändert sonst nichts: Der angezeigte Code bleibt unverändert. Der Hintergrund liegt nur unter Marke und Name der Funktion, nicht unter der ganzen Zeile. Die Aufrufe unter der Funktion öffnen sich von selbst, die nächsten zuerst, bis zu etwa tausend Zeilen; den Rest öffnet der Pfeil. Bräuchten die Wege mehr als etwa zweitausend Zeilen, endet die Liste mit **Zu viele Wege: Die Liste endet an dieser Stelle**, und die weiteren Wege werden nicht gezeigt. Ein weiterer Druck auf die Schaltfläche **Aufrufbaum** beschränkt den Baum auf den geöffneten Weg und die Aufrufe unter der Funktion, und ihr Symbol ändert sich; ein nochmaliger Druck zeigt wieder alle Wege. Im Kontextmenü einer Funktion tut **Nur diesen Weg anzeigen** dasselbe für den Weg dieser Zeile und öffnet deren Funktion, falls eine andere gewählt war; **Alle Wege anzeigen** kehrt zu allen Wegen zurück. Der Einstiegspunkt des Moduls steht vorn, auch wenn eine Analyse ihn umbenannt hat. **Nach Analysestand** fasst die Funktionen danach zusammen, wie weit die Analyse mit jeder gekommen ist: **Vollständig analysiert** — nichts fehlt mehr; **Teilweise analysiert** — ein Teil der Arbeit ist getan, eine Lücke bleibt; **Nur Dekompiler** — Ghidras Name `FUN_…`, kein Kommentar zur Funktion, keine Kommentare zu den Schritten, weder Parameter noch lokale Variablen benannt; **Bibliotheksfunktionen** — Code, den das Modul einbindet, nicht seine eigene Arbeit, nach Kategorie: **EDK2** für die Bibliotheken von EDK2, **AMD AGESA** für die eigenen Bibliotheken von AGESA, **Intel FSP/RC** für die Bibliotheken von Intel FSP und Reference Code und **Kategorie nicht erfasst** für eine Bibliotheksfunktion, die eine frühere Analyse ohne Angabe der Kategorie markiert hat; jede Kategorie öffnet und schließt sich wie eine Gruppe, und die Zahl nach ihr gibt an, wie viele Funktionen sie enthält; **Ohne Rumpf** — eine externe Funktion oder ein Thunk, für die die Analyse keinen C schreibt; **Analysestand nicht erfasst** — eine Analyse, die vor der Aufzeichnung des Analysestands entstand. Jede Gruppe liest sich alphabetisch, und die Zahl nach ihrem Namen sagt, wie viele Funktionen sie enthält; der Pfeil vor einer Gruppe öffnet und schließt ihre Funktionen, und die farbige Marke vor ihrem Namen gibt den Analysestand an: die Farbe der Funktionsnamen im Code für vollständig, orange für teilweise, rot für nur Dekompiler, blau für Bibliotheksfunktionen, grau für Funktionen ohne Rumpf und für einen nicht erfassten Stand. Zwischen dem Umschalter und den Zeilen zeigt ein schmaler Streifen dieselben Gruppen als Anteile an den Funktionen des Moduls, jeder so breit wie seine Anzahl und in der Farbe seiner Gruppe — die Bereitschaft des Moduls auf einen Blick; er wird gezeichnet, solange **Funktionen** gezeigt wird. Der Zeiger über einer Funktion nennt außerdem ihren Analysestand und, wo eine Lücke bleibt, was fehlt. Eine Suche grenzt jede der drei Reihenfolgen ein und zeigt ihre Treffer als eine alphabetische Liste, ohne die Pfeile; eine Überschrift ist keine Zeile und lässt sich nicht auswählen. Eine Funktion, die eine empfangene Revision geändert hat, steht fett mit **Neu** da, solange sie geöffnet ist; die Marke verschwindet beim Wechsel zu einer anderen Funktion. Spätere Revisionen nehmen sie nicht — auch nicht die, die eintreffen, während die App geschlossen ist —, sodass eine noch nicht gelesene Änderung nicht mit der nächsten verloren geht. **Markierungen „Neu“ entfernen**, die Schaltfläche mit dem Auge in der Leiste unter der Liste, nimmt die Marke von allen Funktionen zugleich, und ihre Änderungen gelten als gelesen; die Revisionen bleiben zum Vergleich in der Auswahl. Die Wahl bleibt für den nächsten Code-Bereich erhalten.

Bibliothekscode ist meist in vielen Modulen derselbe: `CopyMem` oder `LibAmdIoWrite` aus AGESA sind in Dutzende Module einer Firmware kompiliert. Eine Bibliotheksfunktion wird im **Bibliotheksregister** gespeichert und nirgends sonst: eine einzige Analyse, die allen Modulen gemeinsam ist, deren Funktion denselben Code hat. Das Modul enthält nur einen Verweis auf den Eintrag; Name, Signatur, Kommentare und C der Funktion liest das Panel aus dem Register. Die Marke **EDK2**, **AMD** oder **Intel** kennzeichnet eine solche Funktion, in der Liste und im Kopf über dem Code; eine Funktion ohne diese Marke gehört dem Modul selbst. Der Zeiger über der Funktion nennt die Version des Eintrags; eine Variante eines Eintrags — derselbe Code, aufgerufen mit anderen Assert-Codes von AGESA — nennt ihre Codes. Unter **Bibliotheksfunktionen** gibt die Zahl nach einer Kategorie an, wie viele Funktionen des Moduls auf Einträge dieser Kategorie verweisen. Alle Module sind gegenüber einem Eintrag gleichberechtigt: Eine Korrektur in einem von ihnen wird zur nächsten Version des Eintrags, und alle Module zeigen diese Version.

**POST-Codes**, die Liste links im Code-Bereich, sind die Werte, die das Modul an Port 0x80 schreibt — das, was eine POST-Karte auf der Platine anzeigt —, jeweils mit der Stelle, von der aus der Wert gesendet wird. Ein Code wird selten dort geschrieben, wo er gesendet wird: Der Wert wird an eine Routine übergeben, etwa `IoWrite8`, ein herstellereigenes `PostCode` oder eine Routine, die den Code schreibt und anhält, und erst diese schreibt ihn an den Port. Die Liste nennt deshalb den Aufruf, der den Wert übergibt, nicht den Schreibzugriff in der Routine. Die Liste ist eine Tabelle: **Code**, **Funktion** — die Funktion, die ihn sendet —, **Über** — die Routinen, die der Wert auf dem Weg zum Port durchläuft — und **Aufrufadresse**; Spalten, die nicht in den Bereich passen, erreicht man durch seitliches Scrollen. Die Codes sind nach dem Wert geordnet, und ein Code, der von mehreren Stellen aus gesendet wird, hat für jede Stelle eine Zeile. Der Zeiger über einer Zeile zeigt außerdem die Breite des Schreibzugriffs. Ein Klick auf eine Zeile wählt die Stelle im ASM-Listing und im C aus und ihre Bytes im Dump; die Liste bleibt dabei vorn. Am Ende der Liste stehen die Schreibzugriffe, die die Analyse nicht auflösen konnte: **Wert unbekannt**, wenn der Wert erst zur Laufzeit ermittelt wird — aus einer Tabelle, in einer Schleife — oder aus Code außerhalb des Moduls stammt, und **Port unbekannt**, wenn schon der Port von außerhalb des Moduls kommt, wie bei einem Dienst, über den andere Module an einen Port schreiben. Das sind Stellen, an denen ein Code gesendet werden kann, keine Codes. Ein Statuscode, der über `ReportStatusCode` gemeldet wird, ist kein Schreibzugriff auf den Port, und welches Byte die Platine für ihn anzeigt, entscheidet das Statuscode-Modul der Plattform: Solche Codes stehen in der Liste **Status**, nicht in dieser. Eine Analyse, die vor dieser Liste entstanden ist, zeigt jeden Schreibbefehl so, wie er lautet; eine erneute Veröffentlichung der Modulanalyse oder eine neue Analyse des Moduls bringt sie auf den neuen Stand.

Auch **Zeichenketten** ist eine Tabelle: **Adresse** — wo die Zeichenkette im Modul liegt — und **Text**. Ein Zeilenumbruch oder ein Tabulator in einer Zeichenkette wird so dargestellt, wie C ihn schreibt, als `\n` und `\t`; so bleibt jede Zeichenkette in ihrer eigenen Zeile. Wo die Spalte den Text abschneidet, zeigt der Zeiger über dem Text die ganze Zeichenkette. Die Liste **Status** enthält die Aufrufe, die `ReportStatusCode` sein können — der Dienst, über den ein Modul einen Statuscode meldet —, jeweils als Kandidat, nicht als gesicherter Befund. Die Analyse sucht sie nur in 32-Bit-PEI-Modulen, in denen der Aufruf über die Tabelle der PEI-Dienste erfolgt; bei jedem anderen Modul — SEC, einem DXE-Treiber, einem 64-Bit-Abbild — ist die Liste leer, und der Bereich weist darauf hin. Eine leere Liste nennt immer den Grund: Die Suche hat nichts gefunden, oder die Analyse hat im Modul nichts dieser Art gefunden. Die Breite der Liste links lässt sich durch Ziehen ihres Rands ändern; jeder Code-Bereich öffnet sich mit der zuletzt gewählten Breite.

## Woher die Namen kommen

Die Namen im Code stammen aus dem Modul selbst. Eine GUID wird nach EDK2 und dem GUID-Katalog benannt; `gBS`, `gRT` und `gST` sind die globalen Variablen, in die die Tabellen geschrieben werden, die der Einsprungpunkt erhält; ein Zeiger auf ein Protokoll oder eine PPI trägt den Namen nach dem Aufruf, der ihn holt; eine Callback-Funktion nach dem Ereignis, für das sie registriert ist. Eine Funktion, für die sich kein Name findet, bleibt `FUN_…` und erscheint grau; beim Überfahren eines rekonstruierten Namens wird angezeigt, woraus er gelesen wurde. Diese Namen sind eine Lesart des Codes, nicht die Namen aus dem Quelltext; wo die Hinweise nicht eindeutig sind, wird kein Name vergeben.
