# Code-Bereich

> Ein Modul als Code gelesen: seine Funktionen, das ASM-Listing, der dekompilierte C und die Bytes, auf die eine Instruktion zeigt.

**Mit Code öffnen** im Baum [[topic:tool-uefi|UEFI-Struktur]] öffnet ein Modul, für das der Speicher eine Analyse hält: die Bytes des Moduls und der Code nebeneinander in einem Fragment-Bereich, benannt nach dem Modul und dem Format des Abbilds, etwa `SecCore ▸ PE32`. Die Analyse ist schreibgeschützt — Änderungen gehören in den Dump —, und der Bereich ist der Ort, an dem sie gelesen wird: die Funktionen links, das ASM-Listing oder der C der gewählten Funktion oben, die Bytes des Moduls unten.

## Der Code

Im Code-Bereich führt der Code dorthin, was er nennt. Ein Klick auf einen Namen hebt jede Stelle hervor, an der er vorkommt: einen Parameter oder eine lokale Variable in der gezeigten Funktion, eine Funktion oder eine globale Variable im C und im ASM-Listing überall dort, wo dieselbe Adresse genannt ist. Ein Klick auf etwas anderes oder **Esc** hebt die Hervorhebung auf. **⌘**-Klick oder Doppelklick auf einen Parameter oder eine lokale Variable wählt die Stelle aus, an der sie definiert ist: den Parameter in der Signatur der Funktion, die lokale Variable in den Deklarationen am Anfang der Funktion. Der Name einer aufgerufenen Funktion ist im C wie im ASM-Listing ein Link, der unter dem Zeiger unterstrichen wird: **⌘**-Klick oder Doppelklick öffnet diese Funktion, und ihre Bytes werden zur Hauptzone des Dumps. Ebenso wählt ein Sprungziel die Instruktion aus, auf der der Sprung landet, und eine globale Variable oder eine GUID deren Bytes im Dump. Die Sprungmarke eines `goto` ist ebenso ein Link: Ein Klick mit **⌘** oder ein Doppelklick wählt die Zeile im C aus, in der die Marke definiert ist, und, solange ihr Name noch die Adresse nennt, auch ihre Anweisung; ein einfacher Klick hebt die Marke überall hervor, wo sie genannt ist. Ein Sprung zu einer Stelle aus der Liste **Verwendet bei** im Popover eines Namens ist ebenfalls eine Bewegung. Solange der Bereich die Tastatur hat, gehen **Darstellung ▸ Zurück** und **Darstellung ▸ Vorwärts** (**⌘[** und **⌘]**) sowie die Pfeile links im Kopf des Bereichs die Stellen zurück und wieder vor, zu denen diese Klicks geführt haben. Eine Stelle wird so wiederhergestellt, wie sie verlassen wurde: ASM-Listing und C sind dorthin gescrollt, wo sie standen, und der Aufruf, dem gefolgt wurde, ist wieder ausgewählt. Eine über einen Link geöffnete Funktion zeigt ihr C von Anfang an. Die Stelle, an der man ankommt — die Zeile der Instruktion im Listing, im C der Aufruf oder der Name der Funktion in ihrer Signatur —, wird kurz hervorgehoben, damit sie leicht zu finden ist.

Solange ein Name hervorgehoben ist, führen **Bearbeiten ▸ Nächstes suchen** (**⌘G**) und **Bearbeiten ▸ Vorheriges suchen** (**⇧⌘G**) von einer Stelle, an der er vorkommt, zur nächsten — im C oder im ASM-Listing, je nachdem, was gezeigt wird: Die Stelle wird ausgewählt, in den sichtbaren Bereich gebracht und kurz markiert. Der Zähler neben **ASM** und **C** gibt an, wie viele Stellen es gibt und bei welcher man ist — der angeklickten oder der zuletzt angesprungenen; seine beiden Pfeile tun dasselbe wie die Tasten. Nach der letzten Stelle geht es reihum zur ersten, und der Bereich zeigt dasselbe Zeichen wie eine Suche, die von vorn beginnt. Ist nichts hervorgehoben, suchen die Tasten wie gewohnt im Dump.

## Namen, die sich selbst erklären

Ein Name, den die Analyse einer Konstante gegeben hat — einem I/O-Port wie `PCI_CONFIG_ADDRESS`, einem MSR, einem Bit eines Chipsatz-Registers —, ein Typ wie eine Struktur und ein Feld einer Struktur erklären sich selbst: Ein Klick darauf öffnet daneben ein Popover. Für eine Konstante zeigt es die Zahl hexadezimal und dezimal, die Gruppe von Namen, zu der sie gehört (etwa `FCH_IO_PORT`), wofür der Name steht, und die Instruktionen, die sie verwenden — ein Klick auf eine davon führt dorthin —, sowie ganz am Ende in kleinerer Schrift die Quelle, aus der diese Angabe stammt. Für einen Typ zeigt es seine Definition mit Offset und Kommentar jedes Felds, für ein Feld dieselbe Definition mit hervorgehobener Zeile des Felds. Auch eine benannte globale Variable des Moduls, etwa `mPciExpressBaseAddress`, öffnet das Popover: ihr Typ und ihre Adresse, der Wert, den das Image dort hält, der Kommentar der Analyse dazu und die Instruktionen, die sie lesen oder schreiben. **⌘**-Klick oder Doppelklick darauf markiert ihre Bytes im Dump, so viele, wie ihr Typ einnimmt. Eine Zahl im ASM-Listing, der die Analyse einen Namen gegeben hat, öffnet dasselbe Popover. Hat die Analyse einen Namen noch nicht erklärt, sagt das Popover dies und zeigt nur die Fakten: den Wert und die Definition des Typs.

Lässt der Decompiler von Ghidra Blöcke aus dem C weg, weil bei den ihm bekannten Werten kein Pfad sie ausführt, sagt das C dies in einer Zeile: `/* WARNING: Removing 74 unreachable blocks */`. Ein Klick auf die Zeile öffnet die Liste der Adressen der entfernten Blöcke; ein Klick auf eine Adresse führt zu den Instruktionen des Blocks im Listing, wo sie alle erhalten sind. Meist ist ein solcher Block Code, den dieser Firmware-Build nie ausführt, etwa ein Zweig für eine andere Einstellung als die dieser Platine. Ein Block, der von der Antwort der Hardware abhängt, kann auf der Platine dennoch ausgeführt werden: eine Prüfung, die im Modell von Ghidra nicht fehlschlagen kann, etwa der Test, ob der Speicher den hineingeschriebenen Wert hält.

## Der Kopf

Der Kopf nennt das Modul, in Klammern die Revision seiner veröffentlichten Analyse — **(r14)** — und nach **▸** die gezeigte Funktion; beide Namen lassen sich markieren und kopieren. Die Zeile darunter nennt die Analyse und die Ghidra-Version, mit der sie erstellt wurde. Sind mehrere Analysen des Moduls gespeichert, ist diese Zeile ein Menü: Jede Analyse ist dort gleich benannt, und eine gewählte stellt den Code des Moduls aus dieser Analyse dar und lässt dieselbe Funktion und Instruktion auf dem Bildschirm. Der eigene Name der Funktion in ihrer Signatur ist kein Link: Diese Funktion ist bereits geöffnet. Wird sie aufgerufen, unterstreicht sich der Name unter dem Mauszeiger wie ein Aufruf, und ein Klick darauf — ebenso **⌘**-Klick oder Doppelklick — öffnet stattdessen **Aufrufe anzeigen…**. Ein Rechtsklick auf den Namen einer Funktion — im Kopf, in der Signatur oder an einem Aufruf im C — bietet **Aufrufe anzeigen…** an; an einem Aufruf steht davor **Gehe zu Definition**, das wie ein **⌘**-Klick die aufgerufene Funktion öffnet. Die Liste öffnet sich als Popover neben dem Namen und nennt jeden Aufruf dieser Funktion, eine Zeile je Aufruf: die aufrufende Funktion, die Adresse des Aufrufs und ihre Instruktion; ein Sprung, mit dem die aufrufende Funktion endet, ist mit **Sprung** markiert. Eine Funktion, die sie zweimal aufruft, steht zweimal da. Eine aufrufende Funktion, die Ghidra kennt, deren Aufruf im Listing aber nicht gefunden wurde — ein Aufruf über einen Zeiger —, steht mit **Aufrufstelle unbekannt** da. Ein Klick auf eine Zeile schließt das Popover und öffnet die aufrufende Funktion an diesem Aufruf, markiert im Listing und im C; eine lange Liste lässt sich im Popover scrollen.

## Beschreibung

**Beschreibung**, die dritte Wahl neben **ASM** und **C**, zeigt anstelle des Codes die Beschreibung des Moduls: wozu das Modul dient, wie es arbeitet und wie es aufgebaut ist — seine Schnittstellen, der Ablauf ab dem Einstiegspunkt, die Funktionen nach ihrer Aufgabe, die angesprochene Hardware, die gemeldeten Codes, die Befunde der Analyse und was noch unbekannt ist. Die Beschreibung entsteht bei der Analyse zusammen mit den Namen und Kommentaren und wird mit ihnen in derselben Revision veröffentlicht; sie beschreibt also stets den gezeigten Code. Eine darin genannte Funktion — als Link oder als Code geschrieben — ist ein Link: Ein Klick öffnet die Funktion im Code, und **Darstellung ▸ Zurück** führt an die Stelle der Beschreibung zurück, an der sie verlassen wurde. Auch ein Klick auf eine Funktion in der Liste links führt zum Code zurück. Hat die Analyse noch keine Beschreibung verfasst, sagt die Ansicht dies. Was eine Beschreibung feststellt, ist die Lesart des Codes durch die Analyse; Unbewiesenes ist als solches gekennzeichnet.

## Einen Namen kopieren

Den Namen des Moduls oben im Code-Bereich kann man auswählen und kopieren, ebenso den Namen einer Funktion in der Funktionsliste: mit **Namen kopieren** im Kontextmenü der Zeile oder mit **Bearbeiten ▸ Kopieren** (**⌘C**), solange die Liste die Tastatur hat.

## Die Listen

Der Umschalter über der Liste wählt, was sie enthält: **Funktionen**, **Zeichenketten**, **POST** oder **Status**. Die erste öffnet eine Funktion — ein Klick auf ihren Namen zeigt ihren Code; die übrigen sind Tabellen dessen, was die Analyse gefunden hat.

Die Marke einer Funktion zeigt, wie weit ihre Analyse fortgeschritten ist, gleich an welcher Stelle der Liste — an der Wurzel des Aufrufbaums, unter der aufrufenden Funktion oder in einer Gruppe: ein `f` auf violettem Quadrat für eine vollständig analysierte Funktion, dasselbe `f` in einem violetten Rahmen für eine teilweise analysierte und violette Säulen für eine Bibliotheksfunktion; eine Funktion jeder anderen Stufe trägt das `f` auf dem Quadrat. Die Leiste unter der Liste enthält das Filterfeld, das die gezeigte Liste eingrenzt, und, solange **Funktionen** gezeigt wird, den Umschalter, der die Reihenfolge der Funktionen bestimmt. **Nach Adresse** ist eine Tabelle der Funktionen, wie die Analyse sie exportiert hat — zuerst die Adresse, dann der Name —, wo jede Funktion im Modul liegt. **Aufrufbaum** stellt jede Funktion unter die, die sie aufruft: eine Funktion, die im Modul niemand aufruft — der Einstiegspunkt, ein Notify-Callback, ein Platz einer Diensttabelle —, beginnt einen eigenen Baum, und was sie aufruft, hängt darunter; der Pfeil vor einer Funktion öffnet und schließt ihre Aufrufe, und die Aufrufe einer Funktion lesen sich alphabetisch. Eine Funktion, die mehrere Aufrufer erreichen, erscheint einmal, beim ersten von ihnen, und der Einstiegspunkt des Moduls steht vorn, auch wenn eine Analyse ihn umbenannt hat. **Nach Analysestand** fasst die Funktionen danach zusammen, wie weit die Analyse mit jeder gekommen ist: **Vollständig analysiert** — nichts fehlt mehr; **Teilweise analysiert** — ein Teil der Arbeit ist getan, eine Lücke bleibt; **Nur Dekompiler** — Ghidras Name `FUN_…`, kein Kommentar zur Funktion, keine Kommentare zu den Schritten, weder Parameter noch lokale Variablen benannt; **Bibliotheksfunktionen** — eine EDK2-Routine, die das Modul einbindet, oder eine mit dem Tag `library`; **Ohne Rumpf** — eine externe Funktion oder ein Thunk, für die die Analyse keinen C schreibt; **Analysestand nicht erfasst** — eine Analyse, die vor der Aufzeichnung des Analysestands entstand. Jede Gruppe liest sich alphabetisch, und die Zahl nach ihrem Namen sagt, wie viele Funktionen sie enthält; der Pfeil vor einer Gruppe öffnet und schließt ihre Funktionen, und die farbige Marke vor ihrem Namen gibt den Analysestand an: grün für vollständig, orange für teilweise, rot für nur Dekompiler, blau für Bibliotheksfunktionen, grau für Funktionen ohne Rumpf und für einen nicht erfassten Stand. Der Zeiger über einer Funktion nennt außerdem ihren Analysestand und, wo eine Lücke bleibt, was fehlt. Eine Suche grenzt jede der drei Reihenfolgen ein und zeigt ihre Treffer als eine alphabetische Liste, ohne die Pfeile; eine Überschrift ist keine Zeile und lässt sich nicht auswählen. Eine Funktion, die eine empfangene Revision geändert hat, steht fett mit **Neu** da, bis sie geöffnet wird. Die Wahl bleibt für den nächsten Code-Bereich erhalten.

**POST-Codes**, die Liste links im Code-Bereich, sind die Werte, die das Modul an Port 0x80 schreibt — das, was eine POST-Karte auf der Platine anzeigt —, jeweils mit der Stelle, von der aus der Wert gesendet wird. Ein Code wird selten dort geschrieben, wo er gesendet wird: Der Wert wird an eine Routine übergeben, etwa `IoWrite8`, ein herstellereigenes `PostCode` oder eine Routine, die den Code schreibt und anhält, und erst diese schreibt ihn an den Port. Die Liste nennt deshalb den Aufruf, der den Wert übergibt, nicht den Schreibzugriff in der Routine. Die Liste ist eine Tabelle: **Code**, **Funktion** — die Funktion, die ihn sendet —, **Über** — die Routinen, die der Wert auf dem Weg zum Port durchläuft — und **Aufrufadresse**; Spalten, die nicht in den Bereich passen, erreicht man durch seitliches Scrollen. Die Codes sind nach dem Wert geordnet, und ein Code, der von mehreren Stellen aus gesendet wird, hat für jede Stelle eine Zeile. Der Zeiger über einer Zeile zeigt außerdem die Breite des Schreibzugriffs. Ein Klick auf eine Zeile wählt die Stelle im ASM-Listing und im C aus und ihre Bytes im Dump; die Liste bleibt dabei vorn. Am Ende der Liste stehen die Schreibzugriffe, die die Analyse nicht auflösen konnte: **Wert unbekannt**, wenn der Wert erst zur Laufzeit ermittelt wird — aus einer Tabelle, in einer Schleife — oder aus Code außerhalb des Moduls stammt, und **Port unbekannt**, wenn schon der Port von außerhalb des Moduls kommt, wie bei einem Dienst, über den andere Module an einen Port schreiben. Das sind Stellen, an denen ein Code gesendet werden kann, keine Codes. Ein Statuscode, der über `ReportStatusCode` gemeldet wird, ist kein Schreibzugriff auf den Port, und welches Byte die Platine für ihn anzeigt, entscheidet das Statuscode-Modul der Plattform: Solche Codes stehen in der Liste **Status**, nicht in dieser. Eine Analyse, die vor dieser Liste entstanden ist, zeigt jeden Schreibbefehl so, wie er lautet; eine erneute Veröffentlichung der Modulanalyse oder eine neue Analyse des Moduls bringt sie auf den neuen Stand.

Auch **Zeichenketten** ist eine Tabelle: **Adresse** — wo die Zeichenkette im Modul liegt — und **Text**. Ein Zeilenumbruch oder ein Tabulator in einer Zeichenkette wird so dargestellt, wie C ihn schreibt, als `\n` und `\t`; so bleibt jede Zeichenkette in ihrer eigenen Zeile. Wo die Spalte den Text abschneidet, zeigt der Zeiger über dem Text die ganze Zeichenkette. Die Liste **Status** enthält die Aufrufe, die `ReportStatusCode` sein können — der Dienst, über den ein Modul einen Statuscode meldet —, jeweils als Kandidat, nicht als gesicherter Befund. Die Analyse sucht sie nur in 32-Bit-PEI-Modulen, in denen der Aufruf über die Tabelle der PEI-Dienste erfolgt; bei jedem anderen Modul — SEC, einem DXE-Treiber, einem 64-Bit-Abbild — ist die Liste leer, und der Bereich weist darauf hin. Eine leere Liste nennt immer den Grund: Die Suche hat nichts gefunden, oder die Analyse hat im Modul nichts dieser Art gefunden. Die Breite der Liste links lässt sich durch Ziehen ihres Rands ändern; jeder Code-Bereich öffnet sich mit der zuletzt gewählten Breite.

## Woher die Namen kommen

Die Namen im Code stammen aus dem Modul selbst. Eine GUID wird nach EDK2 und dem GUID-Katalog benannt; `gBS`, `gRT` und `gST` sind die globalen Variablen, in die die Tabellen geschrieben werden, die der Einsprungpunkt erhält; ein Zeiger auf ein Protokoll oder eine PPI trägt den Namen nach dem Aufruf, der ihn holt; eine Callback-Funktion nach dem Ereignis, für das sie registriert ist. Eine Funktion, für die sich kein Name findet, bleibt `FUN_…` und erscheint grau; beim Überfahren eines rekonstruierten Namens wird angezeigt, woraus er gelesen wurde. Diese Namen sind eine Lesart des Codes, nicht die Namen aus dem Quelltext; wo die Hinweise nicht eindeutig sind, wird kein Name vergeben.
