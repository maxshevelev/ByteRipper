# Codeanalysen und der Analyseserver

> Eine Codeanalyse ist das, was Ghidra in einem PEI- oder DXE-Modul gefunden hat: seine Funktionen, Befehle und den dekompilierten C-Code sowie die Namen, die eine Durchsicht ihnen gegeben hat. ByteRipper liest Analysen aus einem Speicher — einem Ordner auf diesem Mac oder einem Analyseserver, den alle Macs eines Netzwerks gemeinsam nutzen.

Eine Analyse erstellt der Ghidra-Skill außerhalb von ByteRipper. ByteRipper liest, was der Skill gespeichert hat: Ein Modul des UEFI-Baums, zu dem eine Analyse vorliegt, trägt ein Code-Symbol, und **Mit Code öffnen** zeigt seinen Code neben seinen Bytes; der Bereich ist auf [[topic:code-panel|Code-Bereich]] beschrieben. Das Symbol steht hinter dem Namen der Datei des Moduls, ob sie zugeklappt oder aufgeklappt ist, und auch der Abschnitt mit dem Image des Moduls trägt es. Eine zugeklappte Datei oder ein zugeklappter Abschnitt, der die Dateien weiterer Module enthält, etwa ein komprimiertes Volume, trägt das Symbol ebenfalls; eine Liste zugeklappter Zeilen zeigt so, wo analysierte Module liegen. Aufgeklappt überlässt die Zeile das Symbol den Dateien, die sie zeigt. Eine Analyse ist den Bytes des Moduls zugeordnet, nicht dem Dump; dasselbe Modul in einem anderen Dump öffnet daher dieselbe Analyse.

Das Symbol ist ein Kreis, der den Stand der Analyse des Moduls anzeigt. Ein leerer Kreis steht für die automatische Analyse von Ghidra allein: Das Modul wurde noch nicht analysiert. Ein halb gefüllter Kreis steht für eine nicht abgeschlossene Analyse: Eine Funktion ist nicht vollständig analysiert, oder das Modul hat keine Beschreibung. Ein gefüllter Kreis steht für eine abgeschlossene Analyse: Jede Funktion ist vollständig analysiert, mit dem Register der Bibliotheksfunktionen verknüpft oder hat keinen Rumpf, und das Modul ist beschrieben. Eine Analyse, die veröffentlicht wurde, bevor der Analysestand der Funktionen gezählt wurde, zeigt bis zur nächsten Veröffentlichung einen halb gefüllten Kreis. Eine Zeile, hinter der mehrere analysierte Module stehen, zeigt das Symbol des am wenigsten analysierten.

Hinter dem Kreis trägt ein analysiertes Modul ein kurzes Wort in einem farbigen Rahmen: von wem der Code des Moduls stammt, wie die Analyse es festgestellt hat. **EDK2** ist Code, der mit EDK2, dem offenen Referenzcode, übereinstimmt; **EDK2\*** ist ein EDK2-Modul mit Änderungen des Firmware-Herstellers; **AMD** ist AGESA, der Plattformcode von AMD; **Intel** ist FSP oder der Referenzcode von Intel; der Name eines Herstellers, etwa **Insyde** oder **Lenovo**, steht für dessen eigenen Code. Ein durchgezogener Rahmen auf hellem Grund bedeutet, dass die Herkunft festgestellt ist: Der Code wurde mit dem Quellcode verglichen, oder die Herkunft ist in den eigenen Bytes des Moduls genannt. Ein gestrichelter Rahmen mit blasserem Text bedeutet, dass sie aus Zeichenketten, Schnittstellen oder eingebundenen Bibliotheken erschlossen wurde. Konnte die Analyse die Herkunft nicht bestimmen oder hat sie sie noch nicht angegeben, steht kein Wort. Das Wort steht nur an der Datei des Moduls, ob zugeklappt oder aufgeklappt, nicht am Abschnitt mit seinem Image. Der Code-Bereich zeigt den Kreis und das Wort vor dem Namen des Moduls in seiner Titelzeile.

## Wo die Analysen liegen

Der Speicher wird unter **Einstellungen ▸ Codeanalyse** gewählt.

- **Auf diesem Mac** — die Analysen werden aus dem eigenen Ordner dieses Macs gelesen, `~/Library/Application Support/ByteRipper/Analysis`. Dorthin schreibt der Ghidra-Skill, wenn er auf diesem Mac läuft. Diese Einstellung gilt für einen einzelnen Mac.
- **Auf einem Analyseserver** — die Analysen werden von `byteripper-server` gelesen, einem Programm auf einem Rechner im Netzwerk. Alle Macs, die denselben Server angeben, lesen dieselben Analysen; ein einmal analysiertes oder durchgesehenes Modul steht damit allen zur Verfügung.

Die Einstellung legt nur fest, woher die Analysen gelesen werden. Beim Umstellen wird nichts kopiert oder gelöscht: Der Ordner auf diesem Mac bleibt unverändert, und mit **Auf diesem Mac** sind seine Analysen wieder sichtbar.

## Verbindung mit einem Server

Der Server wird einmal eingerichtet, im Terminal des Rechners, auf dem er läuft:

1. `byteripper-server token add --name admin --rights admin` erzeugt das Admin-Token des Servers und gibt es einmal aus. Der Server speichert nur dessen Hash und startet ohne ein solches Token nicht.
2. `byteripper-server token add --name <mac-name> --preset app` erzeugt das Token eines Mac: Jeder Mac und jedes Skript, das den Server liest, hat ein eigenes Token. Das Geheimnis wird einmal ausgegeben und nirgends aufbewahrt.
3. `byteripper-server --listen 127.0.0.1:8765 --listen 100.64.0.7:8765` startet den Server unter den angegebenen Adressen: der Loopback-Adresse für ByteRipper auf dem Server selbst — ein Mac erreicht seine eigene Adresse in einem privaten Netzwerk wie Tailscale nicht — und der Adresse im privaten Netzwerk für die anderen Macs.

Jede Adresse, auf der der Server lauscht, verlangt ein Token, die Loopback-Adresse eingeschlossen. Üblich ist die Adresse des Servers in einem privaten Netzwerk wie Tailscale, das die Verbindung zudem verschlüsselt.

Auf jedem Mac unter **Einstellungen ▸ Codeanalyse**:

1. **Auf einem Analyseserver** wählen.
2. Die Adresse in der Form `http://host:port` — auf dem Server selbst `http://localhost:8765` — und das Token eingeben, das der Server für diesen Mac ausgegeben hat.
3. Auf **Verbinden** klicken.

Die Zeile unter den Feldern zeigt, ob der Server erreichbar ist. Weist der Server das Token zurück oder ist auf diesem Mac kein Token gespeichert, meldet die Zeile genau das und nicht, der Server sei nicht erreichbar; bei einer Zurückweisung nennt sie die Rechte, die dem Token fehlen. Das Token liegt in einer Datei, die nur der angemeldete Benutzer lesen kann, `~/Library/Application Support/ByteRipper/Server/token`. Bleibt das Tokenfeld leer, wird das bereits gespeicherte Token verwendet.

## Arbeiten mit einem Server

- **Neue Analysen erscheinen von selbst.** Der Server meldet jede Änderung sofort; eine von einem beliebigen Rechner gespeicherte Analyse oder veröffentlichte Durchsicht erscheint daher binnen ein bis zwei Sekunden auf allen Macs, und eine offene Codepalette wird an derselben Stelle neu aus ihr aufgebaut.
- **Bereits Gelesenes bleibt lesbar.** Dieser Mac behält eine Kopie dessen, was er vom Server gelesen hat. Der Code einer Funktion wird gelesen, wenn sie angezeigt wird; von einer früheren Revision, mit der eine Funktion verglichen wird, wird nur diese Funktion gelesen. Die Suche, die Liste der Aufrufer einer Funktion und die Liste der Verwendungen eines Namens durchlaufen den gesamten Code des Moduls und lesen deshalb zuerst die übrigen Funktionen. Ist der Server nicht erreichbar, meldet die Zeile in den Einstellungen dies. Bereits Gelesenes wird weiter gezeigt; eine noch nicht gelesene Funktion steht mit ihrem Namen in der Liste, und die Palette meldet, dass ihr Code nicht verfügbar ist. Die Suche und die Listen der Verwendungen erfassen dann nur die bereits gelesenen Funktionen. Die Verbindung wird selbsttätig erneut aufgebaut.
- **Projekte bleiben auf diesem Mac.** Beim Öffnen eines Projekts werden seine Analysen in die Kopie übernommen, die dieser Mac von den gelesenen Serverdaten führt; die Code-Panels zeigen sie so, wie das Projekt sie gesichert hat (siehe [[topic:projects|Projekte]]). An den Server wird nichts gesendet: In seinen Speicher gelangt nur, was über ihn veröffentlicht wird.

## Durchsicht durch einen Agenten

Betreibt der Analyseserver auch Ghidra, kann ein mit ByteRipper verbundener Agent (siehe [[topic:agent|Mit einem Agenten arbeiten]]) dort ein Modul durchsehen: Er öffnet das Modul über einen PE32- oder TE-Image-Knoten des UEFI-Baums, benennt Funktionen, Variablen und Typen, schreibt Kommentare und veröffentlicht das Ergebnis. Jede Veröffentlichung ist eine neue Revision der Analyse des Moduls, und jeder Mac, der den Server liest, zeigt sie. Das Ghidra-Projekt bleibt auf dem Server; eine Durchsicht lässt sich daher später fortsetzen, durch den Agenten oder durch eine Person. Ein Agent, der auf dem Rechner des Servers läuft, verbindet sich direkt mit `byteripper-server`, über dessen lokale Verbindung und nicht über ByteRipper.

Der Server gibt einem Agenten auch seine Rolle und die Regeln der Durchsicht. Ein mit einem solchen Server verbundenes ByteRipper bietet seinen Agenten zwei Vorlagen an — in Claude Code die Befehle `/mcp__byteripper__reviewer` und `/mcp__byteripper__verifier` — sowie die Regeln der Durchsicht als MCP-Ressourcen. Eine mit der ersten Vorlage begonnene Sitzung sieht Module durch und veröffentlicht sie; eine mit der zweiten begonnene prüft deren Ergebnisse und ändert nichts. Solange ByteRipper mit einem solchen Server verbunden ist und das Token Ghidra nutzen darf, zeigt **Einstellungen ▸ Codeanalyse**, wie diese Sitzungen begonnen werden: `claude` im Terminal starten und danach in der geöffneten Sitzung den Befehl der Rolle eingeben. Beim Start lässt sich der Befehl nicht an `claude` übergeben: Claude Code kennt die Befehle von ByteRipper erst, nachdem es sich damit verbunden hat, und meldet ihn vorher als unbekannt. Die Rolle setzt den Namen dieses Macs in den Namen der Sitzung, sodass die Konsole des Servers die Sitzungen verschiedener Macs unterscheidet. Rollen und Regeln gehören dem Server und haben stets dieselbe Version wie seine Werkzeuge; auf diesem Mac muss dafür nichts installiert werden. ByteRipper bewahrt die zuletzt erhaltene Fassung auf und bietet sie an, solange der Server nicht erreichbar ist. Liegen die Analysen auf diesem Mac, werden weder Vorlagen noch Regeln angeboten. Ein Baum der EDK2-Quellen, auf den eine Durchsicht verweist, gehört nicht dazu: Die durchsehende Sitzung bittet einmal darum, ihn zu klonen.

Antwortet ein Werkzeug des Servers falsch oder schlägt fehl, meldet der Agent dies dem Server: den Aufruf, die erhaltene Antwort und das erwartete Ergebnis. Der Server bewahrt diese Meldungen auf; sein Administrator liest sie in der Konsole des Servers auf der Seite **Server Issues** und schließt jede Meldung mit einer Antwort ab: was behoben wurde und in welcher Version, oder warum sich nichts ändert. Die Agenten des Mac, von dem die Meldung kam, lesen die Antworten und handeln danach. Eine Meldung ändert an keinem Modul etwas.

Für die Prüfung der Analysen führt der Server eine Tafel mit Anmerkungen. Ein prüfender Agent trägt, was er in der Analyse eines Moduls für falsch hält, als Anmerkung in das Ticket des Moduls ein – jedes Modul hat genau ein Ticket –, mit Schweregrad und Stelle im Code. Der Agent, der das Modul analysiert, liest die Anmerkungen, beantwortet oder behebt sie und vermerkt dies im Verlauf der Anmerkung. Ein anderer prüfender Agent als derjenige, der das Modul in Arbeit genommen hat, bestätigt jede Anmerkung und schließt das Ticket. Solange eine Anmerkung offen ist, gilt die Analyse des Moduls nicht als abgeschlossen; eine neue Anmerkung öffnet ein abgeschlossenes Modul wieder. Der Administrator liest die Tickets mit ihrem Verlauf in der Konsole des Servers auf der Seite **Review Tickets** und kann dort jeden Status setzen.

Die Typen, die eine Analyse definiert, werden mit den danach analysierten Modulen geteilt. Eine Veröffentlichung, deren Typ vom gemeinsamen nicht nur durch eine Ergänzung abweicht – ein neues Enum-Element, einen Kommentar, einen echten Namen anstelle eines Platzhalters, Felder anstelle unbenannter Bytes –, wird abgelehnt, und es wird nichts geschrieben. Welche Definition richtig ist, entscheidet nicht der Agent, der veröffentlicht. In der Konsole des Servers hat auf der Seite **Activity** jedes Modul unter **Modules in work** eine Schaltfläche, die zeigt, was seine Veröffentlichung ersetzen würde. Bei einem gemeinsamen Typ steht die Definition des Moduls neben der gemeinsamen, zusammen mit dem Modul, das die gemeinsame geschrieben hat. Bei einem Eintrag des Bibliotheksregisters steht jedes Feld, das die Analyse ändert, so, wie der Eintrag es enthält, und so, wie das Modul es schreiben würde, zusammen mit Modul und Revision, die den Eintrag geschrieben haben; der Grund der Änderung ist anzugeben, die Historie des Eintrags bewahrt ihn. **Publish, replacing them** veröffentlicht das Modul im Namen des Agenten, der es in Arbeit hat: Seine Definitionen werden zu den gemeinsamen, als nächste Version der gemeinsamen Typen, und seine Analyse wird zur nächsten Version jedes Eintrags. Die Programme anderer Module ändern sich dabei nicht.

Die Agenten können die Ersetzung einer gemeinsamen Definition – eines gemeinsamen Typs oder eines Eintrags des Bibliotheksregisters – auch untereinander vereinbaren. Der Agent, der das Modul in Arbeit hat, schlägt dessen Definition vor und belegt sie aus dem Code. Der Vorschlag bewahrt beide Fassungen: bei einem Typ die Definition des Moduls und die gemeinsame, bei einem Registereintrag jedes Feld, das die Analyse des Moduls ändert, so, wie der Eintrag es enthält, und so, wie das Modul es schreiben würde. Jeder Agent zählt gleich, ob er auf dem Server arbeitet oder über ByteRipper auf einem anderen Mac; Agenten werden nach dem Namen unterschieden, unter dem sie abstimmen. Stimmen zwei andere Agenten zu und erhebt keiner Einspruch, ersetzt die nächste Veröffentlichung des Moduls den gemeinsamen Typ als nächste Version der gemeinsamen Typen und den Registereintrag als dessen nächste Version; die Historie des Eintrags bewahrt die Begründung des Vorschlags. Voraussetzung ist, dass sich seit der Abstimmung auf keiner Seite etwas geändert hat. Die Module, die die ersetzten Definitionen geschrieben haben, und jedes Modul, dessen Analyse sie verwendet, erhalten daraufhin eine Anmerkung in ihrem Ticket, damit ihre Analysen erneut geprüft werden. Die Vorschläge und ihre Stimmen stehen auf der Seite **Review Tickets**; dort nimmt der Administrator jeden Vorschlag unabhängig von den Stimmen an oder lehnt ihn ab.

## Was der Server nicht tut

- Er ist für das Netzwerk einer einzelnen Person gedacht: Jeder Client hat ein eigenes Token, und dessen Rechte bestimmen, was der Client darf — ein `reader`-Token liest, ein `app`-Token veröffentlicht zusätzlich Durchsichten über den Server. Jeder andere Schreibzugriff auf den Speicher erfordert ein `admin`-Token. Ein eigenes Benutzermodell hat er nicht.
- Er übernimmt keine Analysen von einem Mac. Sein Speicher enthält nur, was über ihn veröffentlicht wurde.
- Er löscht nichts über das Netzwerk. Nicht mehr benötigte Analysen werden auf dem Server selbst mit `byteripper-cas gc` entfernt.
- Er speichert keine Dumps. Eine Analyse vermerkt, welches Modul sie beschreibt, nie die Firmware, aus der es stammt.
