**Open with Code** in the [[topic:tool-uefi|UEFI Structure]] tree opens a module the store holds an analysis of: the module's bytes and its code side by side in one fragment panel, named after the module and the image's format, such as `SecCore ▸ PE32`. The analysis is read-only — editing belongs in the dump — and the panel is where it is read: the functions on the left, the selected function's ASM or C above, the module's bytes below.

## The code

In the code panel the code leads where it names. A click on a name highlights every place it occurs: a parameter or a local in the function shown, a function or a global in the C and in the ASM listing wherever it names the same address. A click on anything else, or **Esc**, removes the highlight. **⌘**-click or a double click on a parameter or a local selects where it is defined: the parameter in the function's signature, the local in the declarations at the top of the function. A called function's name — in the C and in the ASM listing — is a link, underlined under the pointer: **⌘**-click or a double click opens that function, and its bytes become the dump's main zone. A jump's target selects the instruction it lands on, and a global or a GUID selects its bytes in the dump, in the same way. The label of a `goto` is a link in the same way: **⌘**-click or a double click selects the line in the C that defines the label, and the label's instruction when its name still spells its address; a plain click highlights the label wherever it is named. A place opened from **Used at** in a name's popover is a move as well. **View ▸ Back** and **View ▸ Forward** (**⌘[** and **⌘]**), or the arrows at the left of the panel's header, walk back and forth through the places those clicks led to while the panel has the keyboard. A place is returned to as it was left: the ASM listing and the C are scrolled where they were, and the call that was followed is selected again. A function opened from a link shows its C from the top. The place arrived at — the instruction's row in the listing; in the C the call, or the function's name in its signature — flashes briefly so it is easy to find.

While a name is highlighted, **Edit ▸ Find Next** (**⌘G**) and **Edit ▸ Find Previous** (**⇧⌘G**) go from one place where it occurs to the next, in the C or in the ASM listing, whichever is shown: the place is selected, brought into view and briefly marked. The count beside **ASM** and **C** says how many places there are and which one is current — the one clicked, or the last one stepped to — and its two arrows do the same as the keys. After the last place the step goes round to the first, and the panel shows the same sign as a search that has gone round. With nothing highlighted, the keys search the dump as usual.

## Names that explain themselves

A name the review gave a constant — an I/O port such as `PCI_CONFIG_ADDRESS`, an MSR, a bit of a chipset register — a type such as a structure, and a field of a structure explain themselves: a click on one opens a popover beside it. For a constant it shows the number in hexadecimal and decimal, the group of names it belongs to (for example `FCH_IO_PORT`), what the name stands for and the instructions that use it — a click on one of those goes there — and, last, in smaller type, the source the explanation is taken from. For a type it shows its definition with every field's offset and comment; for a field, the same definition with the field's line marked. A named global — a variable of the module, such as `mPciExpressBaseAddress` — opens the popover too: its type and address, the value the image holds there, the review's comment on it and the instructions that read or write it. **⌘**-click or a double click on it selects its bytes in the dump, as many as its type takes. A number in the ASM listing that the review named opens the same popover. Where the review has not yet explained a name, the popover says so and shows only the facts: the value, the type's definition.

When Ghidra's decompiler leaves blocks out of the C because, with the values it knows, no path runs them, the C says so in one line: `/* WARNING: Removing 74 unreachable blocks */`. A click on the line opens the list of the removed blocks' addresses; a click on one goes to its instructions in the listing, where they all still are. Usually such a block is code the firmware build never runs, for example a branch for a setting other than this board's. A block that depends on what the hardware answers can still run on the board: a check that, in Ghidra's model, cannot fail, such as a test that memory holds what was written to it.

## The header

The header names the module, the revision of its published review in brackets — **(r14)** — and, after **▸**, the function shown; both names can be selected and copied. The line under them names the analysis and the Ghidra version that produced it; where the store holds more than one analysis of the module, that line is a menu: each analysis is named there the same way, and one chosen from it draws the module's code from that analysis, with the same function and instruction left on screen. The function's own name in its signature is not a link: it is the function already open. When something calls it, the name underlines under the pointer as a call does, and a click on it — or **⌘**-click, or a double click — opens **Show Callers…** instead. A right-click on the function's name — in the header, in its signature or at a call in the C — offers **Show Callers…**; at a call it first offers **Jump to Definition**, which opens the function called, as **⌘**-click does. It opens as a popover beside the name and lists every call to that function, one row per call: the calling function, the address of the call and its instruction; a jump that ends the calling function is marked **Jump**. A function that calls it twice is listed twice. A caller Ghidra knows but whose call it could not find in the listing — a call through a pointer — is listed with **Call site unknown**. A click on a row closes the popover and opens the calling function at that call, selected in the listing and in the C; a long list scrolls inside the popover.

## Description

**Description**, the third choice beside **ASM** and **C**, shows the module's description in place of the code: what the module is for, how it works and how it is built — its interfaces, the order its entry point runs in, its functions by role, the hardware it touches, the codes it reports, what the review found and what is still unknown. The review writes it together with the names and comments, and it is published with them as part of the same revision, so it always describes the code shown. A function named in it — as a link, or written as code — is a link: a click opens that function in the code, and **View ▸ Back** returns to the description where it was left. A click on a function in the list on the left also returns to the code. A module whose review has not yet written a description says so. What a description states is the reviewer's reading of the code: where it is not proven, it says so.

## Copying a name

The module's name at the top of the code panel can be selected and copied, and so can a function's name in the list of functions: **Copy Name** in the row's right-click menu, or **Edit ▸ Copy** (**⌘C**) while the list has the keyboard.

## The lists

The switch above the list chooses what it holds: **Functions**, **Strings**, **POST** or **Status**. The first opens a function — a click on its name shows its code; the others are tables of what the analysis found.

Every function's name carries a code mark; in the call tree a function shown because something calls it carries a turn-down arrow instead. The switch under the list says how the functions are laid out. **By address** is a table of the functions as the analysis exported them — the address first, then the name — where each function lies in the module. **Call tree** hangs each function under the one that calls it: a function nothing in the module calls — the entry point, a notify callback, a slot of a services table — starts a tree, and what it calls is nested under it; the triangle in front of a function opens and closes its calls, and the calls of one function read alphabetically. A function several callers reach is shown once, at the first of them, and the module's entry point leads even where a review has renamed it. **Grouped by review state** gathers the functions by how far the review has got with each: **Fully reviewed** — nothing keeps it from full; **Partly reviewed** — some work is done and a gap remains; **Decompiler only** — Ghidra's `FUN_…` name, no plate comment, no step comments, no named parameter or local; **Library functions** — an EDK2 routine the module links in, or one tagged `library`; **No body** — an external function or a thunk, for which the analysis writes no C; and **Review level not recorded** — an analysis made before the level was written down. Each group reads alphabetically, and the number after a group's name is how many functions it holds; the triangle in front of a group opens and closes its functions. The pointer over a function also says its level and, where a gap remains, what is missing. A search narrows any of the three and shows its matches as one alphabetical list, without the triangles; a heading is not a row and cannot be selected. A function that a revision the panel received changed reads bold with **New** until it is opened. The choice stays for the next code panel.

**POST codes**, in the list on the left of the code panel, are the values the module writes to port 0x80 — what a POST card on the board shows — each with the place that sends it. A code is seldom written where it is sent: the value is passed to a routine such as `IoWrite8`, a vendor's `PostCode` or a routine that writes the code and stops, and that routine writes it to the port. The list therefore names the call that passes the value, not the routine's write. The list is a table: **Code**, **Function** — the function that sends it — **Through** — the routines the value passes through on its way to the port — and **Call address**; columns that do not fit in the pane are reached by scrolling it sideways. The codes are in order of value, and one code sent from several places has a row for each place. The pointer over a row also shows the width of the write. A click on a row selects the place in the ASM listing and in the C, and its bytes in the dump; the list stays in front. At the end of the list come the writes the analysis could not resolve: **Value unknown** where the value is worked out while the code runs — from a table, in a loop — or comes from code outside the module, and **Port unknown** where the port itself comes from outside the module, as in a service that other modules call to write to a port. These are places where a code may be sent, not codes. A status code reported through `ReportStatusCode` is not a write to the port, and which byte the board shows for it is decided by the platform's status-code module: such codes are in the **Status** list, not in this one. An analysis made before this list existed shows each write instruction as it reads; publishing the module's review again, or analysing the module again, brings it up to date.

**Strings** is a table too: **Location** — where the string is in the module — and **Text**. A line break or a tab inside a string is shown as C writes it, `\n` and `\t`, so every string keeps to its own row; the pointer over the text shows the whole string where the column cuts it. **Status** lists the calls that may be `ReportStatusCode` — the service through which a module reports a status code — each a candidate rather than a conclusion. The analysis looks for them only in 32-bit PEI modules, where the call goes through the PEI services table; for any other module — SEC, a DXE driver, a 64-bit image — the list is empty and says so. An empty list always says why: nothing matches the search, or the analysis found nothing of the kind in the module. The list on the left is made wider or narrower by dragging its edge, and every code panel opens at the width last chosen.

## Where the names come from

The names in the code are read from the module itself. A GUID is named from EDK2 and the GUID catalogue; `gBS`, `gRT` and `gST` are the globals written from the tables the entry point is given; a protocol or PPI pointer is named after the call that fetches it; a callback, after the event it is registered for. A function nothing names stays `FUN_…` and is shown in grey; hovering over a recovered name shows what it was read from. These names are a reading of the code, not the source's own, and where the evidence is not unique the name is left out.
