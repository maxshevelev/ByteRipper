**Open with Code** in the [[topic:tool-uefi|UEFI Structure]] tree opens a module the store holds an analysis of: the module's bytes and its code side by side in one fragment panel, named after the module and the image's format, such as `SecCore ▸ PE32`. The analysis is read-only — editing belongs in the dump — and the panel is where it is read: the functions on the left, the selected function's ASM or C above, the module's bytes below.

## The code

The code is read, not edited, so the C has no text cursor. The line last clicked is marked instead with a light band across the code, as an editor marks the current line. The band is see-through, so the colours of a comparison show under it, and it is hidden while a block of text is selected; **↑** and **↓** move it a line, **Page Up** and **Page Down** a screen, **Home** and **End** to the first and the last line, and the code scrolls to keep it in view. In the ASM listing the selected instruction is marked with the same band, and the same keys move it.

In the code panel the code leads where it names. A click on a name highlights every place it occurs: a parameter or a local in the function shown, a function or a global in the C and in the ASM listing wherever it names the same address. A click on anything else, or **Esc**, removes the highlight. **⌘**-click or a double click on a parameter or a local selects where it is defined: the parameter in the function's signature, the local in the declarations at the top of the function. A called function's name — in the C and in the ASM listing — is a link, underlined under the pointer: **⌘**-click or a double click opens that function, and its bytes become the dump's main zone. A jump's target selects the instruction it lands on, in the same way; the bytes of a global or a GUID are selected by **⌘**-click, since a double click on such a name asks what it is instead. The label of a `goto` is a link in the same way: **⌘**-click or a double click selects the line in the C that defines the label, and the label's instruction when its name still spells its address; a plain click highlights the label wherever it is named. A place opened from **Used at** in a name's popover is a move as well. **View ▸ Back** and **View ▸ Forward** (**⌘[** and **⌘]**), or the **‹ ›** buttons in the toolbar, walk back and forth through the places those clicks led to while the panel has the keyboard or is in front. Past the first of those places Back goes on through the tab's [[topic:navigation|history]]: a place outside the panel puts the panel away, and Forward brings it back. A place is returned to as it was left: the ASM listing and the C are scrolled where they were, and the call that was followed is selected again. A function opened from a link shows its C from the top. The place arrived at — the instruction's row in the listing; in the C the call, or the function's name in its signature — flashes briefly so it is easy to find.

While a name is highlighted, **Edit ▸ Find Next** (**⌘G**) and **Edit ▸ Find Previous** (**⇧⌘G**) go from one place where it occurs to the next, in the C or in the ASM listing, whichever is shown: the place is selected, brought into view and briefly marked. The count beside **ASM** and **C** says how many places there are and which one is current — the one clicked, or the last one stepped to — and its two arrows do the same as the keys. After the last place the step goes round to the first, and the panel shows the same sign as a search that has gone round. With nothing highlighted, the keys search the dump as usual.

## Names that explain themselves

A name the review gave a constant — an I/O port such as `PCI_CONFIG_ADDRESS`, an MSR, a bit of a chipset register — a type such as a structure, and a field of a structure explain themselves: a click on one opens a popover beside it. For a constant it shows the number in hexadecimal and decimal, the group of names it belongs to (for example `FCH_IO_PORT`), what the name stands for and the instructions that use it — a click on one of those goes there — and, last, in smaller type, the source the explanation is taken from. For a type it shows its definition with every field's offset and comment; for a field, the same definition with the field's line marked. A named global — a variable of the module, such as `mPciExpressBaseAddress` — opens the popover too: its type and address, the value the image holds there, the review's comment on it and the instructions that read or write it. **⌘**-click on it selects its bytes in the dump, as many as its type takes; a click and a double click alike open the popover. A number in the ASM listing that the review named opens the same popover. Where the review has not yet explained a name, the popover says so and shows only the facts: the value, the type's definition.

A click on a call of a function opens a popover beside it with the function's review mark before its name, its signature coloured as in the code, the first paragraph of the comment the review wrote over it, which says what the function is for, and **Go to Function**. In the comparison the same click does the same. ⌘-click and a double click go to the function at once, without the popover.

When Ghidra's decompiler leaves blocks out of the C because, with the values it knows, no path runs them, the C says so in one line: `/* WARNING: Removing 74 unreachable blocks */`. A click on the line opens the list of the removed blocks' addresses; a click on one goes to its instructions in the listing, where they all still are. Usually such a block is code the firmware build never runs, for example a branch for a setting other than this board's. A block that depends on what the hardware answers can still run on the board: a check that, in Ghidra's model, cannot fail, such as a test that memory holds what was written to it.

## The header

The head of the list on the left names the module and, in brackets, the revision of its published review — **(r14)**. The line under them names the analysis and the Ghidra version that produced it; where the store holds more than one analysis of the module, that line is a menu: each analysis is named there the same way, and one chosen from it draws the module's code from that analysis, with the same function and instruction left on screen. The header over the code names the function shown, with its review mark before its name. The name of the module and the name of the function can be selected and copied. The pointer over the mark says the level and what is missing, or for a library function what the registry says. The function's own name in its signature is not a link: it is the function already open. When something calls it, the name underlines under the pointer as a call does, and a click on it — or **⌘**-click, or a double click — opens **Show Callers…** instead. A right-click on the function's name — in the header, in its signature or at a call in the C — offers **Show Callers…**; at a call it first offers **Jump to Definition**, which opens the function called, as **⌘**-click does. It opens as a popover beside the name and lists every call to that function, one row per call: the calling function, the address of the call and its instruction; a jump that ends the calling function is marked **Jump**. A function that calls it twice is listed twice. A caller Ghidra knows but whose call it could not find in the listing — a call through a pointer — is listed with **Call site unknown**. A click on a row closes the popover and opens the calling function at that call, selected in the listing and in the C; a long list scrolls inside the popover.

When the analyses are kept on an analysis server, the head of the list on the left shows the state of the server right after the revision. The server sends a short signal every 5 seconds, and the app watches for it. A grey cloud means the signal arrives. An amber cloud with an exclamation mark, in bold lines, means the signal is late, by about 8 seconds: nothing has failed yet. A red cloud with a cross means the connection is lost: no signal for about 20 seconds, no network on this Mac, or a server that does not answer or refuses this Mac's token; the pointer over it gives the reason. The code already read stays readable, and code not yet read cannot be obtained until the cloud returns. While the app is connecting, the cloud pulses. A server of an earlier version sends no signal: the cloud stays amber while it answers, and the app learns of a lost connection only when a request fails, which can take up to a minute. With the analyses kept on this Mac, there is no such icon.

## Description

**Description**, the book at the right of the module's name above the list, shows the module's description in place of the code: what the module is for, how it works and how it is built — its interfaces, the order its entry point runs in, its functions by role, the hardware it touches, the codes it reports, what the review found and what is still unknown. The review writes it together with the names and comments, and it is published with them as part of the same revision, so it always describes the code shown. A function named in it — as a link, or written as code — is a link: a click opens that function in the code, and **View ▸ Back** returns to the description where it was left. A click on a function in the list on the left also returns to the code. The book shows whether the review has written a description yet; while it has not, there is nothing to open. A module that has a description opens on it: the panel shows the description first, and the code is a click on the book or on a function in the list away. A panel opened at a particular function — from a link or an annotation — shows that function. What a description states is the reviewer's reading of the code: where it is not proven, it says so.

The same button hides it again, as does the round close button in the description's top right corner; **ASM** and **C**, the switch over the code, are not shown meanwhile, and no function is named, since the description is about the whole module. A column at the left of the description lists its sections, as the help's contents do, and follows the reading; a click on a section brings it to the top of the view. **View ▸ Back** returns to where the description stood.

## Diff

The bar under the code carries the comparison, as Xcode's does: this revision, the two arrows, a picker of the module's revisions and **Reset**. The picker lists the revisions whose code the store holds, newest first, and picking one turns the C side into a comparison of the function on screen with the same function in the revision picked, line by line — the old and the new line number of each line, what the revision removed on red, what it added on green, and the lines both keep as they were. A function the earlier revision did not have reads as all added, and one the two revisions hold the same is shown as the code, not as a diff of nothing. The code in the diff is drawn by the artifact's own tokens, as the C is, and answers a click as the C does: a name highlights its every occurrence in the diff, ⌘-click follows a call, and a name that explains itself opens its popover — a line of the earlier revision from that revision's reading. The listing stays this revision's: the comparison is the C side's, and the description's. **Reset**, or **No comparison** in the picker, brings the code back. A revision whose code is not yet on this machine is read from the analysis server first, and the comparison appears when it has come; picking again in the meantime replaces the earlier pick. When the code of a revision or of another analysis cannot be read, the panel keeps what it shows, and the reason stays in red on the left of the bar — the object is damaged, or the store does not hold it — until another one is chosen; the reason for a revision is shown with its function. A connection to the server that failed shows only in the cloud at the head of the list. While a read takes long — the code of a revision, the list of the module's revisions, another analysis — the left of the bar shows a moving strip and says what is being read: **Downloading** while a revision's code is coming from the analysis server, **Reading** while this machine reads what it holds. The strip shows that the work is under way, not how much of it is left. When the panel receives a later revision it compares against the one before at once, and opening a function that revision changed puts that comparison on by itself. A mark keeps the earliest revision it was new against, and opening it compares with that one even after further revisions have arrived; while the reader stays on that function, a revision that arrives does not change the comparison. Each function has a comparison of its own: a function the revision did not change is shown as it is, and a function the mark has left is still compared with the revision the mark brought when the reader returns to it, until a later revision marks it again. A revision picked in the bar, and **Reset**, apply to the function on screen alone. These choices last while the panel is open and are not saved in the workspace. The revision each function was last read at is kept with the module between launches, so a revision that arrived while the app was closed brings up as **New** the functions it changed, compared with the revision the reader last read them at. A revision the store has no code for — a history written before revisions kept theirs — is not listed at all. Of the others the picker offers only those that changed the C of the function on screen and read differently from what is shown, so that a choice gives a comparison with something in it; a function no earlier revision differs in offers only **No comparison**. A revision is also listed while it is not yet known what it changed, as in a history a server has not worked through yet. A function marked **New** whose change is not in its code — it was renamed, its signature changed, or the revision added it — carries a yellow plate over the code: the **New** badge beside a title, and a list of what changed besides the code. Where the code reads the same in both revisions the plate says so, since the comparison has nothing to draw. A function whose only difference is its code has no plate: the comparison is the explanation.

While the description is on screen, the same bar compares the description. The picker lists the revisions that changed it, and picking one shows the description as it reads now with the revision's text beside it, as the C is compared: what only the revision picked had is on red, marked −, and what only this one has is on green, marked +. A description the two revisions hold the same is shown as it is. Its links lead to the code in the comparison too. The description has a comparison of its own, apart from every function's: the revision picked for it stays when the reader goes to the code and comes back, and **Reset** applies to it alone. A description that reads otherwise than when the reader last had it open carries **New** to the left of the book; opening it compares it with the revision it was last read at, and the mark goes when the reader leaves it, as a function's does. **Clear New marks** takes it with the functions' marks.

## Searching the code

Over a code panel, **Edit ▸ Find** (**⌘F**) puts the find bar over the code instead of over the module's bytes, and the bar searches text: the C of the function on screen, or the description while it is open. The ASM listing is not searched; a search started while it is shown switches to the C. The bar has no encoding here; **Case Sensitive** and **Whole Word** — a match that is a whole name, not part of a longer one — say how the text is matched. Every match is filled in grey, and the current one is selected, brought into view and marked yellow; the yellow stays until the selection moves. **Return**, **‹ ›**, **Find Next** (**⌘G**) and **Find Previous** (**⇧⌘G**) go from match to match and wrap round at the end, with the same sign as in the dump; a pattern that occurs nowhere is reported by the bar and by a sound. **Use Selection for Find** (**⌘E**) takes the text selected in the C or in the description. The patterns found in code are kept in a **Recent Queries** list of their own, apart from the dump's.

**Edit ▸ Find in All Functions** (**⇧⌘F**), or the magnifier at the end of the switch above the list, shows the Search tab in place of the list: one search over the C of every function of the module and over its description. Its field holds the same pattern as the other search fields of the program; on **⇧⌘F** it is filled with the text selected in the C, or else with the pattern last searched for anywhere. **Return** starts the search; **Case Sensitive** and **Whole Word** act as in the bar, and the menu under the field lists the recent queries. The scope under the field chooses where to look: **Everywhere**, **In Functions** or **In the Description**. Functions whose C the panel has not read yet are read first, which in a large module takes a moment, and the tab says so meanwhile. The result is a tree: each function with a match — with its review mark — or the description, and under it every line that holds the pattern, the match in bold; a match far into a long line is brought forward and the start of the line shortened to `…`. The line above the tree gives the number of results and of functions. A search stops at 5000 results and says that only the first ones are listed: a narrower pattern lists them all. A click on a line, or **↑** and **↓** in the tree, opens the function, or the description, with that occurrence selected and briefly marked. While the result stands, every occurrence of its pattern in the function or the description on screen is filled in grey, as long as the find bar has no matches of its own there.

## Copying a name

The module's name at the top of the code panel can be selected and copied, and so can a function's name in the list of functions: **Copy Name** in the row's right-click menu, or **Edit ▸ Copy** (**⌘C**) while the list has the keyboard.

## The lists

The switch above the list chooses what it holds: **Functions**, **Strings**, **POST** or **Status**. The first opens a function — a click on its name shows its code; the others are tables of what the analysis found.

A function's mark says how far its review has got, wherever the list shows it — at the root of the call tree, under the function that calls it, or in a group: an `f` on a square in the colour of function names in the code for a function fully reviewed, the same `f` in an orange frame for one partly reviewed, and, for a library function, a blue badge with the short name of whose library it is — **EDK2**, **AMD** or **Intel**; a function only the decompiler has seen carries the same `f` in a red frame, one with no body reads it in grey, and a function at any other level the `f` on the square. Each takes the colour of its group's mark. The bar under the list holds the filter field, which narrows the list that is shown, and, while **Functions** is shown, three buttons that say how the functions are laid out. **By address** is a table of the functions as the analysis exported them — the address first, then the name — where each function lies in the module. **Call tree** stands around the selected function and leaves the rest of the module out. It shows every path that leads to the function, from a function nothing in the module calls — the entry point, a notify callback, a slot of a services table — down to the function, all of it open; under the function comes the tree of what it calls, and the calls of one function read alphabetically. Selecting another function draws the tree around that one, every path open again. The arrow in front of a function opens and closes what is under it. A path never passes a function twice; a call back to a function already on the path — a recursive call — is listed with `↺`, without an arrow, and goes no deeper. A circle of calls that nothing outside it calls starts at its first function alphabetically. Where several paths reach the function it is listed at the end of each, and its calls are open at one of these places: the one it was chosen at, or else the first. That place has the background of selected text in the code and, with the path down to it, reads bold; the function's other places have a light grey background and regular type. A click on one of them moves the calls there and changes nothing else: the code on screen stays as it is. The background marks the function's name and mark, not the whole row. The calls under the function open by themselves, nearest first, up to about a thousand rows; the arrow opens the rest. Where the paths would take more than about two thousand rows, the list ends with **Too many ways lead here: the list stops at this point**, and the paths after it are not shown. Pressed again, the **Call tree** button keeps the tree to the open path and the calls under it, and its symbol changes; pressed once more, it shows every path. In a function's right-click menu **Show Only This Path** does the same for the path of that row, and opens that function if another was selected; **Show All Paths** goes back. The module's entry point leads even where a review has renamed it. **Grouped by review state** gathers the functions by how far the review has got with each: **Fully reviewed** — nothing keeps it from full; **Partly reviewed** — some work is done and a gap remains; **Decompiler only** — Ghidra's `FUN_…` name, no plate comment, no step comments, no named parameter or local; **Library functions** — code the module links in rather than its own work, under its kind: **EDK2** for EDK2's libraries, **AMD AGESA** for AGESA's own libraries, **Intel FSP/RC** for those of Intel's FSP and Reference Code, and **Kind not recorded** for a library function an earlier review marked without saying whose; each kind opens and closes like a group, and the number after it is how many functions it holds; **No body** — an external function or a thunk, for which the analysis writes no C; and **Review level not recorded** — an analysis made before the level was written down. Each group reads alphabetically, and the number after a group's name is how many functions it holds; the arrow in front of a group opens and closes its functions, and the coloured mark before its name shows the level: the colour of function names in the code for full, orange for partial, red for decompiler only, blue for library functions, grey for no body and for a level not recorded. Between the switch and the rows a narrow band shows the same groups as shares of the module's functions, each as wide as its count, in its group's colour — the module's readiness at a glance; it is drawn while **Functions** is shown. The pointer over a function also says its level and, where a gap remains, what is missing. A search narrows any of the three and shows its matches as one alphabetical list, without the arrows; a heading is not a row and cannot be selected. A function that a revision the panel received changed reads bold with **New** while it is open, and loses the mark when the reader moves to another function; the mark outlives the revisions that come after it — those that arrive while the app is closed as well — so a change not yet looked at is not lost to the next one. **Clear New marks**, the eye in the bar under the list, takes the mark off every function at once, and what they changed counts as read; the revisions stay in the picker for comparison. The choice stays for the next code panel.

Library code is often the same in many modules: `CopyMem` or AGESA's `LibAmdIoWrite` is compiled into dozens of the modules of one firmware. A library function is stored in the **library registry** and nowhere else: one review, shared by every module whose function has the same code. A module holds only a link to the entry, and the panel reads the function's name, signature, comments and C from the registry. The badge **EDK2**, **AMD** or **Intel** marks such a function, here and in the header over the code; a function without it is the module's own. The pointer over the function names the version of the entry; a variant of an entry — the same code called with other AGESA assert codes — names its codes. Under **Library functions**, the number after a kind is how many of the module's functions link to entries of that kind. Every module is equal with respect to an entry: a correction made in any of them becomes the entry's next version, and every module shows that version.

**POST codes**, in the list on the left of the code panel, are the values the module writes to port 0x80 — what a POST card on the board shows — each with the place that sends it. A code is seldom written where it is sent: the value is passed to a routine such as `IoWrite8`, a vendor's `PostCode` or a routine that writes the code and stops, and that routine writes it to the port. The list therefore names the call that passes the value, not the routine's write. The list is a table: **Code**, **Function** — the function that sends it — **Through** — the routines the value passes through on its way to the port — and **Call address**; columns that do not fit in the pane are reached by scrolling it sideways. The codes are in order of value, and one code sent from several places has a row for each place. The pointer over a row also shows the width of the write. A click on a row selects the place in the ASM listing and in the C, and its bytes in the dump; the list stays in front. At the end of the list come the writes the analysis could not resolve: **Value unknown** where the value is worked out while the code runs — from a table, in a loop — or comes from code outside the module, and **Port unknown** where the port itself comes from outside the module, as in a service that other modules call to write to a port. These are places where a code may be sent, not codes. A status code reported through `ReportStatusCode` is not a write to the port, and which byte the board shows for it is decided by the platform's status-code module: such codes are in the **Status** list, not in this one. An analysis made before this list existed shows each write instruction as it reads; publishing the module's review again, or analysing the module again, brings it up to date.

**Strings** is a table too: **Location** — where the string is in the module — and **Text**. A line break or a tab inside a string is shown as C writes it, `\n` and `\t`, so every string keeps to its own row; the pointer over the text shows the whole string where the column cuts it. **Status** lists the calls that may be `ReportStatusCode` — the service through which a module reports a status code — each a candidate rather than a conclusion. The analysis looks for them only in 32-bit PEI modules, where the call goes through the PEI services table; for any other module — SEC, a DXE driver, a 64-bit image — the list is empty and says so. An empty list always says why: nothing matches the search, or the analysis found nothing of the kind in the module. The list on the left is made wider or narrower by dragging its edge, and every code panel opens at the width last chosen.

## Where the names come from

The names in the code are read from the module itself. A GUID is named from EDK2 and the GUID catalogue; `gBS`, `gRT` and `gST` are the globals written from the tables the entry point is given; a protocol or PPI pointer is named after the call that fetches it; a callback, after the event it is registered for. A function nothing names stays `FUN_…` and is shown in grey; hovering over a recovered name shows what it was read from. These names are a reading of the code, not the source's own, and where the evidence is not unique the name is left out.
