# Update the CPUID brand names

The FIT panel opens a microcode row into one row per CPUID it serves, and each
of those into the models behind it with their S-SPECs (`tool-fit` help page,
`ProcessorNames.swift`). The list is data, generated into:

```
Modules/FITTool/Sources/FITTool/Resources/IntelCPUIDBrandNames.json
```

Intel publishes no machine-readable list of it. The base is the CPUID / brand
name table of the article
`https://comsystem-tlt.ru/obzori/primenenie-cpuid-na-praktike-dlja-zameni-soc--kombajnov-`;
the S-SPECs it leaves out come from Intel ARK and Wikipedia. Everything is
generated by the scripts here, and a run is a diff to read.

```
scripts/import.py       the article → entries; calls enrich.py; writes the JSON
scripts/enrich.py       S-SPECs from ark-sspec.json and Wikipedia, placed by stepping
scripts/ark-sspec.json  what was read from ARK, model by model, with its page
scripts/gaps.py         the models still without an S-SPEC, in batches for ARK agents
scripts/merge_ark.py    an agent batch → ark-sspec.json
scripts/found-sspec.json  codes found by Skills/find-sspec, each with its evidence
scripts/extra-entries.json  CPUIDs the article lacks, each fact with its page
scripts/pins.py         the pinned Wikipedia revisions and Intel commit, moved forward
reference/ark-agent-brief.md   the brief an ARK agent is given
```

All stdlib Python. Use a cache directory outside the repo for what is
downloaded, so reruns are quick and the same.

## Run it

```sh
C=$CLAUDE_JOB_DIR/tmp/cpuid-cache      # or any scratch directory
python3 Skills/update-cpuid-brand-names/scripts/import.py --cache $C
```

It downloads the article (or reads a saved copy:
`import.py page.html --retrieved 2026-11-06`), the Wikipedia pages at the
revisions pinned in `enrich.py`, and Intel's release notes at the pinned
commit; applies `ark-sspec.json`; and writes the JSON. The last line counts the
entries, the models, those still without an S-SPEC, and what ARK and Wikipedia
added. The lines before it say every code it left out and why.

### When the article has changed

`import.py`'s `CORRECTIONS` rewrite four garbled lines of the article, each
keyed by the exact text it replaces; `DROP`, `SERIES` and `FAMILY_CORRECTIONS`
do the same for a truncated number, the series named without models and one
family cell. A correction that no longer matches stops the run and names
itself — read the new line on the page and write the correction again; never
delete one to make the run pass. `CORE_ARCHITECTURES` lists the core names
moved out of a code name's brackets into `cores`; a new hybrid generation adds
its cores there.

## How a code is placed

An S-SPEC belongs to one stepping, and a stepping to one CPUID, so a code goes
in only where it can be put under the right CPUID (`enrich.py`'s header has
the rules in full):

1. The article's own codes stay as they are.
2. A code with a stepping — ARK's, or a Wikipedia row that has one — goes under
   the one entry of that model whose CPUID has that stepping, by Intel's
   release notes (`06-9e-0a` → `906EA` → `U0`) and the article's own steppings.
   Intel's current name for a stepping first (its notes called `06-97-05`
   `C0` until 2022, `H0` since), every name it ever used when that finds no
   one entry. None, or two: left out — unless the model is in one entry only
   and no source gives that entry's CPUID a stepping (Grand Ridge, `B0664`).
3. A Wikipedia code without a stepping goes in only where the article lists
   the model under one CPUID, and only from a page about that entry's
   microarchitecture (`… (Broadwell-based)` gives nothing to an Ice Lake entry:
   the article repeats Broadwell-DE parts there).
4. A code Wikipedia writes for two models (SR3B8, both 8160F and 8160M) or
   that is already another model's is left out.
5. A code from `found-sspec.json` (`Skills/find-sspec`) goes by its stepping
   or its CPUID where its source gives one; a code read from the package's
   marking has neither, and follows rule 3 with one more condition: the
   architecture its source names must begin one of the entry's code names.

A CPUID the article has no row for gets one from `extra-entries.json`, written
after the article's with `"source": "extra"`: code names, cores, families,
segments and models, each with the page that says so (the kernel's
`intel-family.h` for a model number's code name, ARK for the models), and a
stepping only where a page ties it to the CPUID. Its models' codes go in
`ark-sspec.json` like any others. `import.py` refuses an extra entry once the
article has the CPUID: then take it out.

6. A model the article lists under a CPUID it is not sold on is taken out of
   that entry: when it has no code there, ARK gives it steppings none of
   which is the entry's, and another entry of it, whose stepping ARK gives,
   has its codes. A model listed only under such CPUIDs moves instead to the
   one entry whose stepping ARK gives it and which lists a model of its
   series ("Xeon D-15", "Core i7-85"); none or several, and it stays. The
   log names each (`moved:`); a model is never taken out of the table, and
   one without an ARK record is never moved.

Every added code is listed in `sSpecSource` with where it came from (`ark`,
`wikipedia`, and from `found-sspec.json`: `intel`, `database`, `marking`); `sSpecSources` at the top says which revisions and pages.

## Filling the gaps

What neither the article nor Wikipedia gives comes from ARK, and ARK refuses a
script (403) — it is read by agents through WebFetch, and what they find is
kept in `ark-sspec.json` with each model's page, so the next run needs no
network for it.

1. **List the gaps.**

   ```sh
   python3 Skills/update-cpuid-brand-names/scripts/gaps.py --out $C/ark --batches 4
   ```

   `--only ambiguous` for the models under several CPUIDs, where only ARK's
   stepping can place a code; `--only missing` for those with none at all.
   A model ARK was already asked about is not listed again.
2. **Read ARK.** One `general-purpose` agent per batch, in parallel, each given
   `reference/ark-agent-brief.md` with its batch number and directory. About
   twenty models an agent; more and the summaries blur. Batches can run while
   you read the import's diff.
3. **Merge.**

   ```sh
   python3 Skills/update-cpuid-brand-names/scripts/merge_ark.py $C/ark/batch*.json
   ```

   It refuses a code or stepping of the wrong shape, keeps a model nobody
   found (so it is not asked again), and drops the ordering codes.
4. **Run `import.py` again** and read what it left out: a stepping that fits
   no entry is the article placing a model under a CPUID it is not (U0 parts
   listed under `906EB`) — the table is the article's, and that is not ours
   to move.

What the agents read is WebFetch's quotation of the page, not the page: spot-
check a few codes against ARK in a browser before committing a large batch.

What ARK does not give either — Intel's specification updates, S-SPEC
databases, the marking on photographed packages — is `Skills/find-sspec`'s
work, run for a few CPUIDs at a time: it is costly. Its ARK lookups land in
`ark-sspec.json` as these do, the rest in `found-sspec.json`.

## Moving the pins

```sh
python3 Skills/update-cpuid-brand-names/scripts/pins.py          # what moved
python3 Skills/update-cpuid-brand-names/scripts/pins.py --write  # move them
```

Then run `import.py` and read the diff: a new revision can add codes, and can
take some away.

## After a run

1. **Read the diff** of the JSON. New models and codes appear as lines; a
   diff that drops most entries or most codes is a parse that went wrong.
2. **Run the module's tests.**

   ```sh
   cd Modules/FITTool && swift test --filter 'ProcessorNamesTests|FITDisplayTests'
   ```

   They read the shipped file: `90672`'s cores and code names, `806D1`'s two
   groups, `806EA`'s models. A change that moves those is a change to say in
   the commit, with the test.
3. **Do not edit the JSON by hand.** Fix the source in a correction, or the
   ARK record in `ark-sspec.json`, and generate again.

## Rules

- **Nothing invented.** A model the article does not name is not added, a code
  no source gives is not guessed, a stepping is the page's or nothing.
- **Facts only.** The article, ARK and Wikipedia are read for facts — a CPUID,
  a model's name, a code, a stepping. No prose is copied into the JSON.
- **The article's mistakes stay its own.** Where it lists a model under the
  wrong CPUID the table says what the article says; the placement rules keep
  a code from making that look certain, and the help page says the list is
  incomplete. A correction rewrites only what cannot be read at all.
