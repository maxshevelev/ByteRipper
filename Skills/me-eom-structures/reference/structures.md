# Структуры ME: EOM, Boot Guard, OEM Public Key Hash

Что нашлось в дампах ASUS ROG Flow Z13 (CSME 16.1.25.1991, ADP-LP), сверенное с
конфигом MFIT (`Untitled.xml`, сохранённый проект по этому же дампу) и с отчётом
самого MFIT (`orig.cleanME_NO_EOM_info.txt`). Фьюзы PCH здесь не рассматриваются:
из дампа они не читаются.

Это журнал исследования с адресами и значениями; описание структур и того, что
ещё не разобрано у других версий ME, — в `Design/ME_STRUCTURES.md`.

| `CsePlugin:UEP:OemPublicKeyHash` | `05 C6 97 66 … 84 52` (48 байт) | ME-регион, UEP |
| `CsePlugin:UEP:SecondOemPublicKeyHash` | все нули | ME-регион, UEP |
| `CsePlugin:UEP:BtGuardKeyManifestId` | `0x1` | ME-регион, UEP |
| `CsePlugin:UEP:TxtSupported` | `No` | UEP |
| `CsePlugin:UEP:OemKeyRevEnable` | `No` | UEP |
| `CsePlugin:UEP:PrtcBackupPower` | `None` | UEP |
| `CsePlugin:UEP:FdvEnabled` | `No` | UEP |
| `CsePlugin:UEP:RpmcSupported` / `RpmcRebindEn` | `Yes` / `Yes` | UEP |
| `CsePlugin:UEP:BtGuardCpuDebugEnable` / `BtGuardBspInitEnable` | `Enabled` | UEP |
| `CsePlugin:UEP:PttSupportedFpf` / `DnxEnabled` | `Yes` / `Yes` | UEP |
| `CsePlugin:UEP:OemPlatformId` / `UniquePlatformId` | `0x0` / `0x0` | UEP |

Дословно из help_text (это и есть ответ на «где ключ и как понять, задан ли он»):

> **OEM Public Key Hash** — «Raw hash string for the **SHA-384 hash of the OEM public key**
> corresponding to the private key used to sign the OEM Key hash manifest. When
> manufacture is completed, this hash value is **burned into an FPF**, and is
> permament. … **OEM signing is disabled when this hash is set to all 0s.**»

> **EOM on First Boot Enabled** — «This setting determines if End of Manufacturing
> will be triggered on first boot of the platform after flashing. Note: **When this
> setting is enabled Intel(R) CSME will enter End of Manufacturing regardless of
> the descriptor settings.**»

> **Flexible EOM setting options** — `['Lock Descriptor and OEM Configs',
> 'Lock OEM Configs Only', 'Lock Descriptor Only', 'Do not lock Descriptor and OEM
> Configs']` — «determines which settings will be automatically commited during
> End of Manufacturing flows».

Отчёт MFIT по cleanME-образу (`orig.cleanME_NO_EOM_info.txt`) печатает те же три
факта человеческими строками — по нему и надо сверять наш вывод:

```
CsePlugin#OEM_KM starting offset: 0x198000
Intel (CS)ME Region version 16.1.25.1991 (Clean, Configured)
Boot Guard Status: BG0 - Boot Guard Disable NO_FVME
EOM (End of Manufacturing) on First Boot Disabled
OEM Public Key Hash (SHA-384): 05c697663a75e912…d2e6fd3e8452
```

## Что это значит для определений

1. **OEM Public Key Hash** = `CsePlugin:UEP:OemPublicKeyHash`, 48-байтный SHA-384,
   в области **UEP** ME-региона. Задан ⇔ не все нули (по help_text: «OEM signing is
   disabled when this hash is set to all 0s»). В Z-дампе встречается **12 раз**:
   6 — в ключевой таблице MFS (по 0x21CFCA, 0x21D0D2, 0x21D2E2, 0x21D3EA, 0x21D5FA,
   0x21D702) и 6 — в UEP (по 0x2A00A0, 0x2A0150, 0x2A0250, 0x2A10A0, 0x2A1150,
   0x2A1250). Второй хеш
   (`SecondOemPublicKeyHash`) — нули; на BIOS-стороне живёт **другой** 32-байтный
   хеш (`Boot Guard Key Manifest`, FIT → 0xF49B00, хеш по 0xF49B24) — это не он.
2. **Уровень Boot Guard** = `CsePlugin:UEP:BtGuardProfileConfig`, значения
   `0 - No_FVME`, `3 - VM`, `4 - FVE`, `5 - FVME`. MFIT пишет его **в образ** —
   но не в UEP, а JSON-записью в разделе CDMD (ниже): там он и читается из дампа.
   Проект по Z_FLOW объявляет `5 - FVME`.
3. **EOM**:
   - `mca/eom` (1 байт) = `EOM#EomFirstBootEnabled` (0/1) — «закроет ли при первой
     загрузке»; в заводском дампе 0x00, в образе `cleanME_EOM` 0x01;
   - `mca/eom_config` (2 байта) = `EOM_Config#FlexibleEomSettings` — перечисление
     из четырёх значений (что именно фиксируется при EOM); в заводском 0x0000.
   Обе записи есть и в OEM-конфигурации (заводское значение), и в живой ФС (что
   стоит сейчас); `/home/mca/eom_flow` — маркер без заводской записи.

## Форматы, проверенные побайтно

- **Дескриптор**: подпись `5A A5 F0 0F` по 0x10, FLMAP0 0x14, FLMAP1 0x18; таблица
  регионов по `(FLMAP0>>16 & 0xFF) << 4` (счёт в старшем байте здесь 0, читать все
  16 слотов), секция мастеров по `(FLMAP1 & 0xFF) << 4`; слово BIOS-мастера
  (v2): `read = w>>8 & 0xFFF`, `write = w>>20 & 0xFFF`. Заводское `0x00F/0x00A`;
  в `cleanME_NO_EOM` — `0xFFF/0xFFF`; в `cleanME_EOM` — `0x00F/0x11A` (это уже
  работа MFIT: он запирает дескриптор той же операцией, что выставляет флаг).
- **OEM-конфигурация (FITC)**: по `payloadOffset` u32-счётчик записей, далее по
  12 байт `{fileID, offset, flags}`; значение = байты по `payloadOffset + offset`.
  File ID: `eom` 0x10020000, `eom_config` 0x1001EE00, `manuf_lock` 0x10020100.
  Суммы: `dataCRC` (FITC+0x0C) = CRC-32 (zlib) по payload; `headerCRC` (+0x04) =
  CRC-32 по первым 12 байтам с обнулённым полем.
- **MFS-файл**: содержимое = первые `size` байт цепочки, далее 16 служебных байт,
  в конце 40-байтная таблица Integrity.
- **UEP** (0x2A0000, 8 КБ в этих образах): контейнер `$UEPC`, по +4 — **16-битная
  сумма CRC и два зарезервированных байта** (не размер: так устроен класс `Uep`
  у FIT, см. ниже); записи вида `{…, 0x4FE | 0xFE, <адрес окна в BIOS-регионе>,
  <размер>, <сумма>, <Key Manifest ID>, <48-байтный хеш>, …}`; вторая часть
  области начинается по 0x2A1000. В заводском дампе полезная часть записана, у
  образов MFIT — стёрта/иная (13 мелких различий в шапке и суммах).

## Профиль Boot Guard читается из JSON в CDMD

**Профиль в образе есть**, и моё прежнее «не отражается» было ошибкой: пара
`image_BG3.bin` / `orig.cleanME_EOM.bin` оказалась одним и тем же файлом сборки с
профилем 0 (внутри него самого стоит `0`), так что она ничего про профиль не
доказывала.

Источник — раздел **CDMD** (`0x29D000·0x3000` в этих образах, начинается строкой
`FIT AS A FIDDLE`): внутри лежат маленькие JSON-записи настроек, среди них

```
{"BtGuardProfileConfig": 3}
```

Число — **индекс в списке MFIT**: `0` = `0 - No_FVME`, `1` = `3 - VM`,
`2` = `4 - FVE`, `3` = `5 - FVME`. Проверено по всем дампам с известным уровнем:

| дамп | JSON | профиль | истина владельца |
|---|---|---|---|
| `Z_FLOW…orig.bin` | `3` | 5 - FVME | 5 ✓ |
| Legion `SPI_ALL.bin` | `3` | 5 - FVME | 5 ✓ |
| `orig.cleanME_NO_EOM` / `_EOM` / `image_BG3` | `0` | 0 - No_FVME | 0 ✓ |
| `image_BG4.bin` | `2` | **4 - FVE** | 4 ✓ |
| Lenovo `1.bin` / `2.rom` | строки нет | битами в UEP (см. ниже) | 0 |

Читается поиском ASCII-строки `"BtGuardProfileConfig"` и числа за ней; рядом в том
же блоке лежат и другие настройки (в `image_BG4` — ещё `{"FpfSvnEnabled": 1}`).
Где блока нет вовсе (`1.bin`, `2.rom` — образы без CDMD-конфигурации), профиль из
дампа не выводится *этим* путём: там остаются вторичные признаки — вендорские
манифесты KM/BPM в BIOS и заполненный UEP. Сам UEP позже оказался читаемым
(«Профиль у CSME 15 всё-таки читается — битами в UEP» и «fit-14.0.exe разобран»).

Прежняя, ошибочная версия этого раздела опиралась на пару `image_BG3` и
`orig.cleanME_EOM`, отличавшуюся **22 байтами**:

| адрес | BG3 | BG0 | что это |
|---|---|---|---|
| 0x80–0x93 | `00 0F A0 11 …` | `FF …` | мастер-секция дескриптора (заперта из-за EOM) |
| 0x29500C | `A0 B3 5B 66` | `EF 7E 4B 90` | `dataCRC` OEM-конфигурации |
| 0x296F20 | `01 01` | `00 00` | записи `eom` и `eom_config` |

Это различия **EOM**, а не профиля — что верно и по сей день: они и есть след
включения «EOM on first boot» (запертый дескриптор + записи о фиксации).

Что дамп показывает про Boot Guard: **номер профиля** — из JSON в CDMD (выше);
**OEM Public Key Hash** — в UEP (и его зеркало в `3LVLSCD.dat`); вендорские
манифесты KM/BPM в BIOS-регионе и состояние дескриптора — вторичные признаки.
Когда блока CDMD нет, последние остаются единственной опорой.

## Оракул: ожидаемые строки

`scripts/me_eom.py` печатает эти три факта построчно. Проверенные значения (по ним
и сверять правки скрипта); адреса — файловые, то есть от начала дампа:

| дамп | дескриптор BIOS-мастера | `eom` / `eom_config` (FITC 0x295010) | профиль из CDMD |
|---|---|---|---|
| `Z_FLOW…orig.bin` | `0x00F / 0x00A` (locked) | `00` / `00 00` | `3` → **5 - FVME** |
| `orig.cleanME_NO_EOM` | `0xFFF / 0xFFF` (open) | `00` / `00 00` | `0` → 0 - No_FVME |
| `orig.cleanME_EOM` | `0x00F / 0x11A` (locked) | `01` / `01 00` | `0` → 0 - No_FVME |

Вторая раскладка профиля — запись области у CSME 12–14 — печатается отдельной
строкой (`UEP record flags: …`). Её ожидаемые значения: у четырёх сборок
`~/Downloads/1/csme14-bg{0,3,4,5}.bin` — **0, 3, 4 и 5**, у дампа CSME 14
`SPI_EF4018_128Mbit.orig.bin` — 0 (он и есть основа этих сборок), у четырёх образов
CSME 12 с нулевым полем ключа — 0, у пары с ключом (`W25Q256JV.orig.bin`, Dell
Optiplex) — 5. У образов 15/16 эта строка отвечает «no CSME 12–14 record here».

Хеш Z-дампа — 48 байт `05c6 9766 …` — встречается в образе **12 раз**: оракул
печатает это одной строкой (`12 copies`), из них 6 — в UEP (0x2A00A0, 0x2A0150,
0x2A0250, 0x2A10A0, 0x2A1150, 0x2A1250) и 6 — в ключевой таблице MFS
(0x21CFCA, 0x21D0D2, 0x21D2E2, 0x21D3EA, 0x21D5FA, 0x21D702). Прежняя запись «15
раз» была артефактом: окно, сдвинутое на 4 байта, попадало в соседнюю запись и
считалось отдельным значением; точное сравнение даёт 12. Строки оракула ниже
первого значения (`fe 04 00 00 …`, `367afcca …`, `01 00 00 00 …`) — окна,
захватившие хвост соседней записи, а не другие ключи.

Что оракул **не** печатает: живое значение записей `eom`/`eom_config` — он читает
страницу заводских значений OEM-конфигурации (ту, что есть и в чистом образе). Что
стоит сейчас, лежит в файловой системе MFS, и это читает движок приложения.

Блок CDMD в этих образах лежит по 0x29D000 (сигнатура `FIT AS A FIDDLE`) и несёт
рядом с профилем настройки стенда: `StrapsProject`, `HarnessProject`,
`HarnessLabel`, `HarnessRevision`, `SelectedRvp`, `DbC_Strap_CSME_USB2_DbC_port_enable`,
`ResizeNftpForFtpr`, `sku`, `FpfSvnEnabled` — то есть читать из образа можно не
только профиль. Из этих же строк видно, что `FpfSvnEnabled` у сборок MFIT стоит, а
у заводского Z-дампа его нет.

### Прежняя гипотеза (опровергнута)

Ранее по слову `container+0x68` предполагалось одноразрядное кодирование профиля:
`0x00` = профиль 0, `0x04` = профиль 5. Опыт BG3 её снял: у профиля 3 третий байт
тоже `0x00`, а слово целиком (`0x000000FE`) совпадает с образом профиля 0. Бит
`0x400` отличает **заполненный** UEP (образ с платы, где manufacturing прошёл) от
пустого UEP сборки MFIT или образа обновления, а не уровень.

## Слово настроек UEP: чем «настроен» отличается от «не настроен»

Первые 0x100 байт контейнера UEP — фиксированные поля, и одно из них
(`u32` по `container+0x68`) отличает образы с **заполненным** UEP (снятые с платы,
прошедшей manufacturing) от образов, где UEP пуст (сборки MFIT, образы обновления).
Сводка по 36 дампам коллекции (`~/Desktop/ME` и дампы ASUS/Lenovo):

| `+0x68` | дампы |
|---|---|
| `0x000004FE` | ASUS Z Flow (orig_30072026.BIN — копия того же), Dell SPI_EF4020 |
| `0x0000047E` | ASUS SPI_C27519, Dell SPI_EF4019, Lenovo LENV_all, Lenovo SPI_ALL_192Mbit, **Lenovo Legion SPI_ALL** |
| `0x00000472` | CSME 15.bin, Dell SPI_204319 |
| `0x00000172` | 1.bin, 1.bin_S0, 2.rom (Lenovo, ключ `3bec…`) |
| `0x000000FE` | CSME 16.1.bin, оба образа MFIT (`cleanME_NO_EOM`/`cleanME_EOM`), `image_BG3` |
| `0x0000007E` | LENV_CSME 16.bin (чистый образ Lenovo), HP EliteBook 630 |
| `0x00000000` | CSME 12.BIN, DELL Optiplex 5070, HP ProDesk, GD25B127D, SPI_EF4018, Original_Bios |

Слово читается как **битовая карта настроек UEP**: младшие два байта — булевы
поля (`0xFE` = семь «Yes»: RpmcSupported, RpmcRebindEn, BtGuardCpuDebugEnable,
BtGuardBspInitEnable, PttSupportedFpf, DnxEnabled и ещё одно), бит `0x400`
второго байта — «UEP заполнен» (он же отличает `0x172`/`0x4xx` серийных плат от
`0x00xx` сборок). Смена профиля это слово не меняет — см. опыт BG3 выше.

Сверка двух проектов по полям дала соответствие одного бита младшего байта:
у ASUS `DnxEnabled = Yes` и бит `0x80` выставлен, у Legion `DnxEnabled = No` — и
бит снят; остальные булевы поля у них совпадают. Это одна пара, то есть бит под
`DnxEnabled` пока лишь правдоподобен.

Соседние поля — не настройки, а окно в BIOS-регионе и его сумма, они разные у
каждого образа: `+0x6C` адрес (0x79ED80, 0x40ED80, 0x03FBED80…), `+0x70` размер
(0x180000, 0x80000), `+0x7C` 32-битная сумма, `+0x80` = Key Manifest ID (0x1).

## Что дамп всё-таки говорит про Boot Guard

Признак, который сработал на всех проверенных парах — **наличие вендорских
манифестов в BIOS-регионе**:

| плата | уровень (со слов пользователя) | `__KEYM__` (Key Manifest) | `__ACBP__` (Boot Policy) | ключ в UEP |
|---|---|---|---|---|
| ASUS Z Flow | 5 | есть (0xF49B00 и копия 0xE59080) | есть (0xF49080 и 0xDF0300) | `05 C6 97 …` |
| Lenovo Legion 5 Pro | 5 | есть | есть | `7C CA BE …` |
| Lenovo 1.bin / 2.rom | 0 | **нет** | **нет** | `3B EC …` (заполнен) |
| cleanME_NO_EOM (сборка MFIT) | 0 (отчёт MFIT) | есть — BIOS вендорский, подпись выключена | есть | `05 C6 97 …` |

То есть у платы, где Boot Guard включён, BIOS несёт Key Manifest и Boot Policy
Manifest (их и показывает панель FIT по записям FIT-таблицы), а у платы с
профилем 0 в этой BIOS их нет вообще. Сборка MFIT сохраняет вендорский BIOS, а с
ним и его манифесты, поэтому по сборке уровень не проверяется — только по дампу с
платы.

Второй признак, годный только для дампа **с платы** (UEP заполнен движком):
бит `0x400` в слове `container+0x68`. По подтверждённым владельцем дампам:
Z Flow (профиль 5) — `0x4FE`, Legion (5) — `0x47E`, то есть бит есть; Lenovo
1.bin / 2.rom (профиль 0, но UEP заполнен и ключ `3B EC …` на месте) — `0x172`,
бита нет. У сборок MFIT UEP пуст, и бит ничего не значит.

**Номер профиля читается из JSON в CDMD** (раздел выше) — манифесты же несут
лишь ту политику, которой подписаны, и вторым признаком не являются. Если блока
CDMD в образе нет (`1.bin`, `2.rom`), строка панели может честно сказать только
«Boot Guard включён: манифесты и ключ есть» / «выключен: ни манифестов, ни ключа»,
и тогда номер берётся с живой платы через MEInfo — либо остаётся неизвестным.

## База настроек внутри mfit.exe — точная карта FPF/UEP

MFIT возит с собой XML-базу настроек в сжатом виде (zlib-потоки внутри
`mfit.exe`). Она даёт не только имена и значения, но и **физическую карту**: для
каждой настройки — файл (или структура) и смещение с битами. Карта FPF/UEP
(36 полей; смещения внутри структуры, где `OEM_KH_0` — по 0x98):

| поле | смещение | биты |
|---|---|---|
| `OEM_CFG_DONE`, `GLITCH_D_EN` | 0x40 | 0, 1 |
| `OEM_ID` / `KM_ID` / `FW_TYPE` / **`BTG_PROFILE`** | 0x48 | 0–15 / 23–26 / 27–29 / **30–32** |
| `FTPM_EN`, `RPMC_EN`, `FDV_EN`, `TXT_EN`, `OEM_KH_0_V`, `KM_ID_V`, `BTG_PROFILE_V`, `BSP_INIT_DIS`, `CPU_DEBUG_DIS` … | 0x4c | по одному биту |
| `PLAT_ID` / `DNX` / `RPMC_RB` / `CSE_FW_SVN_EN` … | 0x84 | 0–15 / 16 / 17 / 20 |
| **`OEM_KH_0`** / **`OEM_KH_1`** | 0x98 / 0xC8 | 384 бита (48 байт SHA-384) |

Значения профиля: `0 - No_FVME`, `3 - VM`, `4 - FVE`, `5 - FVME` (из
`config_params` настройки), а сам `BtGuardProfileConfig` лежит в секции
`BootGuardConfiguration`.

Для EOM та же база даёт раскладку файла `mca/eom_config` (2 байта): **бит 0 =
`EomFirstBootEnabled`**, **биты 1–2 = `FlexibleEomSettings`** (0 = «Lock Descriptor
and OEM Configs», 1 = «Lock OEM Configs Only», 2 = «Lock Descriptor Only», 3 = «Do
not lock…») — то есть наш образ с `eom_config` = `0x0001` читается как
«EOM при первой загрузке: да, фиксировать дескриптор и OEM-конфигурацию».

Чего карта не решает: в *вендорских* дампах контейнер UEP устроен иначе, чем
ожидает карта (`$UEPC` против `$UEP`, несколько записей с ключом, вторая часть
области по 0x2A1000), поэтому запись с живыми значениями ещё надо опознать —
для этого нужен внешний оракул, и им служит ECFinder.

## Внешний оракул: ECFinder

`ECFinder.exe` (<https://…/Downloads/ECFinder_0>, readme на русском) умеет по дампу
печатать «Boot Guard Status» и сохранять «OEM Public Key Hash (SHA-384)» в
`…_info.txt`; его отчёты владелец дампов и присылал. Что показали прогоны:

| файл | `Boot Guard Status` | состояние ME в его же строке | истинный профиль |
|---|---|---|---|
| `Z_FLOW…orig.bin` | `BG5 - Boot Guard Enabled FV_VME` | Not clean, **Initialized** | 5 |
| `image_BG3.bin` | `BG0 - Boot Guard Disable NO_FVME` | Clean, **Configured** | 0 (файл равен сборке BG0) |
| `orig.cleanME_EOM.bin` | `BG0 - … NO_FVME` | Clean, Configured | 0 |
| Z-дамп с погашенным битом `0x400` в UEP | `BG5` (не изменилось) | Not clean, Initialized | — |
| сборка BG0 с выставленным битом `0x400` | `BG0` (не изменилось) | Clean, Configured | — |

Отсюда: **бит `0x400` к вердикту отношения не имеет** (копии не изменили ответ), а
вердикт идёт в паре с состоянием файловой системы ME: «Initialized» → `BG5`,
«Configured» → `BG0`. Гипотеза, которая сходится со всеми четырьмя файлами:
**«Boot Guard настроен» = в BIOS есть вендорские манифесты (KM/BPM) И файловая
система ME инициализирована**. Проверка, которая её закроет: `1.bin` / `2.rom` —
профиль 0, манифестов нет, но UEP заполнен (ME работал). По гипотезе ECFinder
скажет `BG0`, по «состоянию ME» — `BG5`, по «маскам дескриптора» — тоже `BG5`
(у них те же `0x00F/0x00A`, что у Z-дампа).

Важно для строки в панели: **сам номер профиля (3/4/5) ECFinder не читает** — он
печатает двухзначный вердикт («настроен/нет»). Номер при этом в образе есть
(CDMD-JSON, раздел выше), и ECFinder его просто не смотрит: `image_BG4.bin`
(профиль 4) по нашей гипотезе получит у него `BG0`, как соседний `image_BG3` —
различие 4 против 0 на вердикт не влияет, поскольку он идёт в паре с состоянием
файловой системы ME. Это **предсказание, не проверенное** — прогон ECFinder по
`image_BG4` его закрывает.

## Что ещё не разобрано (честно)

- ~~**По чему именно ECFinder решает «настроен/нет».**~~ **Отвечено автором
  ECFinder (26-я сессия, со слов владельца):** на 16-й версии он смотрит **только
  флажок EOM** и по нему строит отчёт. Права в дескрипторе он не читает, поэтому
  на образе, который закроет Manufacturing правами, его строка будет говорить не
  то, что сделает плата — наша диагностика шире. Из четырёх наших отчётов это
  сходится с тремя (`Z_FLOW…orig` — живой `eom` = 1; `image_BG3` — `eom` = 01 в
  FITC; `zflow_bit400_cleared` — то же, что Z-дамп); четвёртый
  (`cleanme_bit400_set`) перепроверить нельзя — сам файл удалён, а его отчёт
  говорит «Enabled».
- **Область CDMD разобрана не полностью.** Опознаны подпись `FIT AS A FIDDLE`,
  адрес блока конфигурации и ключ `BtGuardProfileConfig`; остальные записи того же
  блока (сколько их, есть ли среди них настройки EOM) не перечислены. Стоит снять
  список всех JSON-ключей по всем дампам — это и есть карта настроек, читаемых из
  образа.
- **Номер профиля читается** — из CDMD-JSON там, где блок есть, и из UEP-области
  там, где его нет: битами у CSME 15/16, записью области у CSME 12–14 (оба опыта
  проведены, см. выше). Внешним оракулом (ECFinder) сверены только 15/16-е
  значения; у 12–14 опора — сборки с известным профилем.
- **Флаги политики внутри Boot Policy Manifest.** Манифест разобран приложением
  только по версии, revision и SVN (`Packages/UEFIImage/.../FITComponents.swift`);
  где в его заголовке лежат биты политики и как они соответствуют профилям 3/4/5 —
  не установлено, и без платы с уровнем 3 или 4 не установится.
- **Семантика полей записи UEP**: адрес/размер окна (в Z-дампе 0x79ED80 и
  0x180000 — окно внутри BIOS-региона), 32-битная сумма 0xCAFC7A36, ключ Manifest
  ID. Формально MFIT пишет `BtGuardKeyManifestId = 0x1`, и `01 00 00 00` в записи
  ему соответствует.
- **Ключевая таблица MFS против UEP**: хеш лежит 12 раз — 6 записей в таблице
  MFS и 6 в UEP, и одна только эта таблица (48 записей по 48 байт) даёт понять,
  что ключевых входов несколько. Что именно она перечисляет (шесть раз один и тот
  же хеш с разными назначениями?) и зачем в UEP шесть копий, не доказано.
- **Противоречие в правилах MFIT**: сборка отказывается ставить флаг при
  `0xFFFF` в правах BIOS-мастера («not allowed»), а help_text того же поля
  говорит, что при включённом флаге CSME войдёт в EOM «regardless of the
  descriptor settings». Что из этого верно на платформе — проверяется дампом
  после первой загрузки.

## Как читать

`scripts/me_eom.py <dump>…` печатает: состояние дескриптора (заперт ли BIOS-мастер),
адрес `$UEPC` и долю стёртого, записи OEM-конфигурации для трёх EOM-файлов и
повторяющиеся 48-байтные значения ME-региона (хеши ключей). Скрипт — оракул
исследования, не финальное правило: эвристику по 48-байтным повторам заменит
разбор записей UEP, когда профиль будет заякорен.

## Чем кончилось: три факта в панели

Исследование доведено до строк ME Analyzer (коммит «ME Analyzer: Manufacturing,
Boot Guard and the OEM public key hash as rows»). Движок решает так:

- **права доступа в дескрипторе** решают, когда флага нет или он выключен: заводские
  права (в этих дампах `0x00F/0x00A`) закрывают Manufacturing при первом
  включении, а `0xFFF/0xFFF` служебного образа — нет. Это то, на что изготовители и
  полагаются: **флаг в 0 ничего не значит**;
- **страница образа** — записи раздела FITC, те же File ID (эпоха 0xC, размеры 1
  и 2 байта), и она решает флаг: её платформа и применяет при EOM;
- **живые записи файловой системы** (`/home/mca/eom_config` = индекс 197, File ID
  0x1001EE00) читаются **по File ID** через `FileTable.dat` — они нужны только
  тогда, когда образ отдают без раздела OEM-конфигурации, поэтому без базы живая
  страница не читается, и это видно в основании;
- **`eom` (индекс 90, File ID 0x10020000) в вывод не входит**: он говорит, что
  Manufacturing закрывали на *той* плате, с которой снят дамп, а вопрос строки —
  про машину, в которую образ только будет записан (требование владельца). Но
  именно он и подтверждает модель: у **всех** дампов с `eom` = 1 ответ выходит
  «закроет» — либо флаг, либо заводские права, — а единственный «не закроет»
  это образ, собранный самим владельцем с открытым дескриптором;
- **флаг, выставленный при открытом дескрипторе**, — отдельный вывод («закроет,
  но дескриптор открыт»): такую комбинацию MFIT собирать отказывается;
- **`FlexibleEomSettings`** — биты 1–2 той же записи `eom_config`, отдельной
  строкой сводки в четырёх значениях MFIT («Зафиксировать дескриптор и
  OEM-конфигурацию» … «Не фиксировать ничего»). Хранится независимо от флага,
  поэтому образ без флага всё равно говорит, что зафиксировал бы, если бы
  закрывал;
- **профиль Boot Guard** — `{"BtGuardProfileConfig": n}` из CDMD; **хеш ключа** —
  **поле самой записи UEP**: 0xA0 байт от контейнера `$UEPC`/`$UEP` и ещё 0x10A0
  от него же во второй половине области. Так читается на всех дампах под рукой
  (CSME 12–18) и даёт ровно то же значение, что раньше давала эвристика «самый
  частый повтор», зато читает и те образы, где повтор не складывался (CSME 18).
  Что лежит в поле, то и есть вывод: **все нули** — «подпись OEM отключена»,
  **всё FF** — область не писали, **иное** (указатель, иная раскладка) —
  «структура не распознана» (так отвечают CSME 14 и CSME 11).

  История вопроса: сначала ключ искали по повтору и печатали «материала ключа
  нет» там, где повтор не находился; затем порог подняли до трёх вхождений, после
  того как на CSME 18 значение нашлось по одному разу на половину — но проверка
  слота показала, что право и это значение, и порог был неверен. Читать надо поле,
  а не считать повторы.

Проверено на дампах с известным ответом (значения — вывод `MEFirmwareCLI`):

| дамп | Manufacturing | отчего | Boot Guard | хеш ключа |
|---|---|---|---|---|
| `Z_FLOW…orig.bin` | **закроет** | заводские права (флаг 0) | 5 - FVME | `05C69766…` |
| `orig.cleanME_NO_EOM` | **не закроет** | флаг 0 и открытый дескриптор | 0 - No_FVME | `05C69766…` |
| `orig.cleanME_EOM` | **закроет** | флаг 1 | 0 - No_FVME | `05C69766…` |
| `image_BG4.bin` | **закроет** | флаг 1 | **4 - FVE** | `05C69766…` |
| `1.bin` / `2.rom` (CSME 15) | **закроет** | флаг 1 | записи о профиле нет | `3BEC6173…` |
| `CSME 15.bin` | **закроет** | заводские права (флаг 0) | записи о профиле нет | `12CD1095…` |
| `CSME 12.BIN` | **закроет** | заводские права (флага нет вовсе) | записи о профиле нет | материала ключа нет |

У всех дампов с живой записью `eom` = 1 (плата действительно закрыта) ответ —
«закроет» ✓; у единственного образа, который владелец собирал, чтобы **не**
закрывать (`cleanME_NO_EOM`), дескриптор открыт ✓. Модель сходится с живыми
данными.

### Что говорит база настроек самого MFIT

Извлечённая из `mfit.exe` база (`mfit_settings.xml`) называет **одну и ту же
настройку дважды**, и это источник путаницы:

```xml
<File path="mca/eom_config" alias="EOM_Config">
  <LogicalAccess name="EomFirstBootEnabled">   offset=0 length=2 bit_low=0 bit_high=0
  <LogicalAccess name="FlexibleEomSettings">   offset=0 length=2 bit_low=1 bit_high=2
      config_params="{'Lock Descriptor and OEM Configs':'0', ... 'Do not lock':'3'}"
<File path="mca/eom" alias="EOM">
  <LogicalAccess name="EomFirstBootEnabled">   offset=0 length=1 data_type=Raw
```

То есть **бит 0 файла `eom_config` — это флаг** (`EomFirstBootEnabled`), **биты
1–2 — `FlexibleEomSettings`, нумерация с нуля** ✓ (наш движок читает именно так),
а файл `mca/eom` — **вторая копия того же флага**, отдельным байтом.

Чего база **не** знает вовсе: `mca/manuf_lock` (ни одного упоминания), и никакой
настройки вроде «EOM закрыт». То есть «замок производства» — не настройка сборки,
а файл, который пишет платформа.

### Проверка на запросе владельца (LENV_all.orig.bin, CSME 16.0.15.1662) Живые
записи файловой системы читаются так (`MEFirmwareCLI`, адреса — файловые):

| запись | LENV_all | CSME 15.bin | orig_30072026 | Z-дамп |
|---|---|---|---|---|
| `/home/mca/eom` | **0x01** | 0x01 | 0x01 | 0x01 |
| `/home/mca/eom_config` | **0x00** | 0x00 | 0x00 | 0x00 |
| `/home/mca/manuf_lock` | **0x01** | 0x01 | 0x01 | 0x01 |
| флаг в FITC | 0 | 0 | 0 | 0 |
| дескриптор | заперт | заперт | заперт | заперт |

Полные данные по четырём дампам (записи FITC — страницы образа, «живые» — файлы
файловой системы):

| дамп | FITC `eom` | FITC `eom_config` | FITC `manuf_lock` | живой `eom` | живой `eom_config` | живой `manuf_lock` |
|---|---|---|---|---|---|---|
| Z-дамп | 00 | 00 00 | 00 | **01** | 00 | **01** |
| LENV_all | 00 | 00 00 | 00 | **01** | 00 | **01** |
| CSME 15.bin | 00 | 00 00 | 00 | **01** | 00 | **01** |
| 1.bin / 2.rom | 01 | 01 00 | 00 | 01 | 01 | **01** |

Что из этого **следует**, а что — нет:

- **Следует:** `manuf_lock` сборка не пишет никогда (во всех образах 00) и его нет
  в базе MFIT, а на всех платах он 1 → его пишет платформа. `eom` — вторая копия
  флага; в трёх образах FITC говорит 00, а живой байт 01 → его тоже переписала
  платформа (в `1.bin` флаг и в образе 1). `eom_config` живой **повторяет**
  FITC-запись — то есть платформа его не меняет.
- **Не следует:** что именно платформа имела в виду, записав `eom` = 1 и
  `manuf_lock` = 1. Документации на это нет; ни у одного дампа с работающим
  движком эти байты не равны 0, так что «они отмечают именно закрытие EOM» —
  это **вывод**, а не факт. Записи выглядят как отметки о том, что платформа
  проходила через EOM, но подтверждения этому у нас нет.

**Проверено на живом включении** (владелец, Lenovo Legion 5 Pro 16IAH7H NM-E231,
CSME 16.0.15.1662): `image.bin` — образ, который прошили, `image.after.bin` —
дамп той же платы после первого включения. Флаг `EOM on first boot` был **выключен**.

| | `image.bin` (прошит) | `image.after.bin` (после включения) |
|---|---|---|
| дескриптор, мастер BIOS | `0xFFF/0xFFF` — открыт | **открыт, байт в байт тот же** |
| File System State | Configured | **Initialized** — движок отработал |
| FITC / CDMD / UEP | — | **не изменены ни на байт** |
| живой `eom` | (файловой системы нет) | **0x00** |
| живой `eom_config` | — | **0x00** |
| живой `manuf_lock` | — | **0x00** |
| что платформа записала | | только том MFS и его окружение (IVBP, FLOG, EFS, MPHytbl): 180 566 байт, 59 участков |

Отсюда:

- **признаков закрытия нет**: дескриптор остался открытым (и закрыться не мог —
  флаг 0, права открыты), дескрипторная область в дифе не отличается вовсе;
- **`eom` и `manuf_lock` остались нулями**, хотя платформа заведомо отработала —
  она построила файловую систему с нуля (Configured → Initialized) и записала
  180 КБ. То есть эти два байта **не** отмечают «платформа просто запускалась»:
  на закрытых платах они читаются 1 именно из-за закрытия. Контрольный случай
  для догадки из предыдущего раздела получен;
- вердикт строки для этого образа был «**Не закроет**», и включение это
  подтвердило. Второй источник для других версий ME — отчёты MFIT и ECFinder:
  строка ECFinder про EOM на паре «до/после» скажет о смысле байтов то же.

**Вторую половину пары на живой плате ставить нельзя.** Образ с включённым флагом
закрыл бы Manufacturing по-настоящему: хеши ключей уходят во фьюзы чипсета и
обратно не вынимаются. «Закрытая» сторона сравнения берётся из заводских дампов
(Z Flow, Legion, служебные образы Lenovo), и именно она нужна для чтения образа.
Строчка эта существует ровно для того, чтобы не нажимать на это вслепую.

Живые записи печатает харнес (`MEFirmwareCLI`, строки `live record:`); в панели
их нет намеренно — строка отвечает за следующее первое включение, а не за
историю платы. У не-FTBL томов (CSME 12) харнес их не читает: файлы там не несут
File ID, и сопоставление по ID даёт чужие файлы.

Строка показывается для CSME 11 и новее: права доступа читаются из дескриптора
второй редакции (v2, от Skylake), а до CSME 11 этого механизма в нашем разборе
нет.

В панели ни `eom`, ни `manuf_lock` не показываются — строка отвечает за
следующее первое включение (`ManufacturingState`). Их печатает только харнес
(`live record:`), и то как «что лежит в файловой системе», без утверждения о
закрытии.

Цвет строки по требованию владельца: «не закроет» — зелёный (плата
запустится и останется доступной для работы), «закроет» и «закроет при открытом
дескрипторе» — тот же цвет, что состояние Initialized (образ себя фиксирует).

**Уточнение владельца, изменившее вывод** (25-я сессия): «если EOM стоит в 0, это
не значит, что Manufacturing не будет закрыт: это определяется правами в
дескрипторе; изготовители флаг не ставят, ограничиваясь правами; флаг ставится
только явно через MFIT». Первая редакция строки этого не учитывала и читала флаг 0
как «не закроет».

**Новое, чего не знали:** у образов CSME 15 записи `BtGuardProfileConfig` в
CDMD нет вовсе (`1.bin`, `2.rom`, `CSME 15.bin`; у них и сигнатуры
`FIT AS A FIDDLE` нет). Их доски по ECFinder — BG0, то есть профиль 0, но
**дамп этого не говорит**: панель пишет «записи о профиле нет», а не «0».
Профиль туда попадает другим инструментом вендора (или у CSME 15 он лежит в
ином месте, которое мы ещё не нашли) — это открытый вопрос для CSME 15.

## FIT 15 (`fit-15.0.exe`): где те же структуры у поколения 15

`fit-15.0.exe` — консольная (Qt) сборка FIT 15.0, и внутри неё те же данные, что
у MFIT 16, только в другой упаковке и другой схеме. Ресурсы лежат zlib-потоками
прямо в exe — **с тем же ключом, что и у MFIT**: искать не `\x78\x9C`, а
`\x78[\x01\x9c\xDA]` (иначе часть потоков не находится; на этом я в прошлый раз
и споткнулся). В 15.0 таких потоков 131, из них 88 — именованные XML, имена
хранятся в дереве ресурсов в UTF-16.

Раскладка ресурсов — **по платформам**, и платформа опознаётся по списку
`<Include href=":/res/xml/...">` внутри документа:

| документ | что это |
|---|---|
| `<платформа>_fit_layout_<SKU>_<версия>.xml` | раскладка: настройки, их типы, метки, help, структуры, стропы |
| `<платформа>_fit_cfg_dflt*.xml` | значения по умолчанию |
| `<платформа>_straps.xml` | стропы дескриптора |
| `<платформа>_uep.xml` | область UEP и FPF (то, где живут профиль Boot Guard и хеш ключа) |
| `res/bin/TGL_ftbl.bin` | **таблица файлов** (сигнатура `FTBL`), то есть тот самый File Table |
| `res/bin/sam_pphy/*`, `res/bin/pmc_vr/*` | образы SAM/PPHY (CPD) и PMC |

Платформы внутри 15.0: TGL/TGP (это и есть ME 15), ADL-P/S, ICL/ICP, EHL, JSL,
LKF, FHF, CML/CMP, WTL, EGS, DG1/DG2, PVC, MGR, ATS, BXT.

**Привязка настройки к файлу и смещению** у 15 выражена не записью
`<LogicalAccess>`, а действием модуля `Nvar`:

```xml
<Action name="ProcessNvar" module="Nvar" target="ProcEmulation"
        params="{'filePath':'$FilePaths/ME_CONF_WRK','cellIndex':'40',
                 'cellOffset':'8','cellSize':'12','bitHi':'3','bitLo':'0',
                 'isBitfield':'true'}" />
```

Смещение = `cellIndex × cellSize + cellOffset` (для не-битовых полей вместо
ячейки стоит `startOffset`, размер — `varSize`), файл берётся из класса
`FilePaths` (`ME_CONF_WRK` → `policy/cfgmgr/cfg_rules`). Таких привязок в 15.0
**1341 на 117 имён**. Словари значений — классы: `NoYesValues` (`No`=0, `Yes`=1),
`EnabledDisabledValues` (**`Enabled`=0, `Disabled`=1** — обратный порядок!),
`FlexibleEomSettingsValues`, `BootGuardProfiles` — в общем документе
(`lkf_fit_layout_1_7_common.xml`).

**Проверено на дампах.** Привязки TGL дают `ProcEmulation` = 40×12+8 = **488** и
`MELanPowerWell` = 15×12+8 = **188**, а `FID_PAV` (наш `PavpSupported`) =
28×12+8 = **344** — те же смещения, что в базе MFIT 16 для ADL-S. Прогон карты
ME 16 по дампам CSME 15: у `CSME 15.bin` и `1.bin` все значения `cfg_rules`
попадают в свои словари (`PavpSupported = Yes`, `MELanPowerWell = SLP_LAN#`,
`MEWlanPowerWell = SLP_WLAN#`, `ProcMissingDetect = No` (0xFF), `ProcEmulation` —
одна из семи эмуляций), а по всем четырём дампам (`CSME 15.bin`, `1.bin`,
`2.rom`, `orig_30072026.BIN`) воспроизводятся факты, установленные раньше руками:
`CSME 15.bin` — флаг в FITC 0 и живой `mca/eom` = 1; `1.bin` и `2.rom` — флаг 1
в обоих; `orig_30072026` — флаг 0 в FITC и живой `mca/eom` = 1. То есть раскладка `cfg_rules` у 15 и 16
на этих платформах **одна и та же** — но карту для 15 всё равно надо выпускать
из базы 15-й: поколение без своей карты не читается вовсе, а не чужой картой.

**Где лежит то, из-за чего CSME 15 отвечает «записи о профиле нет».** В
`<платформа>_uep.xml` (в 15.0 это отдельные документы `Class`-корня, 20–56 КБ):
сигнатура области — `$UEP` (`SignatureVal = 0x50455524`), не `$UEPC` как у 16, а
поля FPF описаны записью в битовые массивы:

```xml
<Action name="GetBitArrayValue" module="Bin" source="$PlatformIntegrity/OemKeyRevEnable"
        target="UepBitsArray2" params="{'offset':'0x30','startBit':16,'bitCount':1}"/>
```

Одно и то же поле пишется в три массива (`0x30`, `0x54`, `0x58`) — это те самые
несколько копий области, что видны в дампах. Отсюда и надо брать профиль Boot
Guard и хеш ключа для 15-го: не из CDMD (его у 15 нет), а из FPF внутри UEP.

### FPF для 15-й: карта есть, места в дампе — нет

В тех же `_uep.xml` (в 15.0 это отдельные документы с корнем `Class`, 18–56 КБ)
лежит **карта полей FPF**: 252 поля, у каждого — смещение, `startBit`,
`bitCount` и массив, в который оно пишется (`UepBitsArray0…7`), плюс сама
структура области:

```
$UEP | CRC(2) | Reserved(2) | data: { UepBitsArray0…7, по 0x80 байт }
```

Блок Boot Guard в первом массиве, по смещению 0x60 (биты внутри двойного слова):

| бит | поле |
|---|---|
| 16 | `$BootGuardProfileSettings/FBGAcmEn` |
| 17 | `$BootGuardConfiguration/BtGuardCpuDebugEnable` |
| 18 | `BtGuardBspInitEnable` |
| 19 | `ProtectBiosEnvironment` |
| 20 | `$BootGuardProfileSettings/MeasuredBoot` |
| 21 | `VerifiedBoot` |
| 22–25 | `BtGuardKeyManifestId` |
| 0x64:4, 0x64:5 | `ErrorEnforcement_0/1` |

А в классе `BootGuardProfiles` того же инструмента — **таблица самого Intel**,
какому набору флагов соответствует каждый профиль:

| профиль | FBGAcmEn | Verified | Measured | Protect | ErrorEnf |
|---|---|---|---|---|---|
| 0 — No_FVME | нет | нет | нет | нет | 0xC |
| 3 — VM | нет | да | да | да | 0xC |
| 4 — FVE | да | да | нет | да | 0xF |
| 5 — FVME | да | да | да | да | 0xF |

И ещё: `ProcessProfile` связывает выбор профиля (`$BootGuardConfiguration/BtGuardProfileConfig`)
не с числом в образе, а с этими флагами — «инструмент выводит их из выбора»,
что и объясняет, почему у FIT 15 в раскладке нет поля с номером профиля.

**Что с этим можно и чего нельзя.** Якорь расположения подтверждён: хеш ключа
лежит в **0x98 второго массива** (`0x80 + 0x18`) — это ровно тот же байт, что
движок читает как `+0xA0` от контейнера, и он сходится на всех четырёх дампах
CSME 15. Но **флаги по 0x60 первого массива нулевые во всех образах под рукой** —
в том числе в двух, где CDMD прямо говорит профиль 5 (`orig_30072026.BIN`,
`GZ301ZEF1.317` Асуса). То есть либо массивы в вендорском дампе лежат не там, где
их кладёт инструмент, либо биты в этих образах не заполнены — и читатель,
поверивший в смещение, отвечал бы «0 - No_FVME» **любому** образу, у которого
ключ не пуст, и ошибался бы ровно на тех двух. Поиск базы перебором по битовой
картине бесполезен: подходящих баз в области тысячи (биты дешёвы), отличить
правильную нечем.

**Чем это решается** (без платы): собрать FIT 15 **два образа из одного проекта,
отличающихся только профилем** (0 и 5), и сравнить области UEP. Различающиеся
биты и есть блок профиля в настоящем образе — тот же приём, которым в проекте уже
проверяли MFIT. Пока этого нет, панель для 15-й честно отвечает «записи о профиле
нет», и это остаётся открытым вопросом.

### Три сборки, отличающиеся только профилем: где профиль *не* лежит

Владелец собрал в FIT 15 три образа из одного проекта — `csme15-bg0.bin`,
`csme15-bg3.bin`, `csme15-bg5.bin` (профили 0, 3, 5). SHA-256 у всех трёх разные,
размер один (32 МБ) — то есть сравнение содержательное (та самая проверка,
которой не сделали в прошлый раз).

**Профиля нет в образе числом.** Во всех трёх нет ни одного байта, ни одного
двойного слова, где стояло бы 0 / 3 / 5 соответственно: перебор по всему файлу —
ноль совпадений. Это ровно то, что обещает раскладка FIT: «`ProcessProfile`
берёт выбранный профиль и **выводит** из него флаги», поэтому числа в образе и
нет.

**Различия сосредоточены в одном месте.** Расхождения: область EFS региона ME
(0x463000–0x473000) и несколько байт в UEP (сдвиг адреса окна и поле размера
`$UEP`), а **BIOS-регион побайтно одинаков** во всех трёх. Внутри EFS — таблица
записей по 24 байта: перестановка чисел 0…13, шесть нулевых байт и четырёхбайтная
сумма (класс `KeyManifestHashUsages` у FIT 15 называет манифесты, которым эти
хеши принадлежат).

| сборка | записей всего | из них фиксированных | в «хвосте профиля» |
|---|---|---|---|
| bg0 (профиль 0) | 48 | 47 | **1** |
| bg3 (профиль 3) | 56 | 47 | **9** |
| bg5 (профиль 5) | 64 | 47 | **17** |

Фиксированные 47 записей побайтно одинаковы во всех трёх, хвост растёт **на 8
записей на шаг профиля**, и он **кумулятивен**: девять записей bg3 — побайтный
префикс семнадцати записей bg5. То есть образ CSME 15 говорит о своём профиле не
полем, а **длиной этой таблицы**.

**Профиль 4 собран — и таблица профиль *сборки* называет, а профиль платы нет.**
Четыре сборки дают 48 / 56 / 72 / 64 записей для профилей 0 / 3 / 4 / 5, и списки
**строго вложены**: 48 ⊂ 56 ⊂ 64 ⊂ 72, каждый шаг ровно 8 записей (профиль 0 →
профиль 3 → профиль 5 → профиль 4 — порядок не совпадает с номерами профилей, FVE
оказался самым длинным). То есть у **сборки** профиль виден по длине таблицы, и все
четыре различимы.

А у **дампов плат** — нет: та же таблица там своя на каждую плату (у `CSME 15.bin`
30 записей, у `1.bin` 33, у `orig_30072026.BIN` 18, у `image.after.bin` 21), общих с
набором сборки — единицы, и **ни в одном нет записей-шагов профиля**. В том числе в
`orig_30072026.BIN`, у которого CDMD прямо говорит профиль 5. Значит, таблица —
это набор манифестов и их хешей **данного образа**, а не утверждение платы о своём
уровне Boot Guard: шаги профиля дописывает инструмент при сборке, и на плате их
может не быть вовсе.

Формат записи, если понадобится дальше: 24 байта — перестановка чисел 0…13, шесть
нулевых байт, 4-байтная сумма; таблица начинается с тождественной перестановки
`00 01 02 … 0D`.

**Таблица — это журнал сборок (проверено пятой сборкой).** Владелец собрал
`csme15-bg00.bin` — профиль 0, но уже после всех остальных. В ней **80 записей**:
первые 72 **побайтно совпадают** с `csme15-bg4.bin`, и добавлены ровно 8 новых.
Счётчики в начале различающихся блоков (`0x465000` и соседние) идут 8, 9, 10, 11,
12 — то есть это **номер сборки** (7 + N), а не что-либо о профиле. Значит таблица
дописывается: каждая сборка добавляет **8 записей**, и они не константа профиля, а
**переход** от прежнего состояния к новому — у `bg00` (профиль 0) добавленная
группа не равна группе `bg0` (тоже профиль 0), потому что шла от профиля 4.

Структура записи, как она выглядит: 24 байта — перестановка чисел 0…13, у которой
позиции 5…9 всегда `05 06 07 08 09`, шесть нулевых байт и 4-байтная сумма; соседние
записи в группе отличаются **одной транспозицией**, то есть группа — это «шаг за
шагом» путь из одного порядка в другой, восемь шагов на сборку.

**Начало таблицы одинаково у сборки и у живой платы.** Первые **40** записей
`csme15-bg0.bin` **побайтно совпадают** с таблицей реального дампа `CSME 15.bin` (там
её длина 40). То есть эта часть — не история конкретной сборки, а нечто
платформенное: один и тот же порядок записей у собранного образа и у платы. У
`1.bin` и `2.rom` (другая платформа/SKU) с началом bg0 совпадают только первые 12.

**Общее начало — это входной образ, а не платформа.** Владелец подтвердил: все
пять сборок сделаны **из `CSME 15.bin`**. Значит совпадение первых 40 записей
объясняется тривиально — они были в исходном образе, и каждая сборка дописывала
свои 8 поверх. Никакой «платформенной базы» тут нет.

**И добавленные группы не зависят от профиля так, чтобы по ним читать.** Сравнил
пять групп попарно как **наборы** записей: пересечение **ноль из восьми** у всех
пар, в том числе у двух сборок с *одним и тем же* профилем 0 (`bg0` и `bg00`) —
и это при том, что обе шли из одного проекта и одного входного образа. Состояние
хода зависит от того, откуда он начался, и по нему профиль не восстанавливается.

Что записи вообще такое: таблица начинается с **тождественной перестановки**
`00 01 02 … 0D`, постоянны позиции `02` и `05…09` (шесть значений), свободно
переставляются восемь остальных. И это **один непрерывный ход**: каждый следующий
элемент отличается от предыдущего **одной транспозицией** (изредка двумя; в `bg00`
таких шагов 12 из 79), причём ход **не начинается заново на границе сборки** — восемь
записей на сборку это просто продолжение той же трассы. Значит таблица — журнал
последовательных состояний одной перестановки, а не набор блоков по сборкам; поэтому
в ней и нет ничего, что называло бы профиль.

**Таблицы родственны внутри семейства образов, но не по профилю.** `1.bin`
(дамп работающей платы, профиль 0 по словам владельца) — все 59 записей являются
**побайтным префиксом** таблицы `2.rom` (156 записей): это один и тот же образ,
прошедший больше сборок. А `CSME 15.bin` (тоже плата с профилем 0) с ними делит
только 12 записей — другое семейство. Внутри семейства общее начало есть, между
семействами его нет, и ни в одном из сравнений не видно ничего, что зависело бы от
профиля: две платы с профилем 0 из разных семейств не похожи друг на друга сильнее,
чем плата с CDMD=5 на плату с CDMD=0 из одного семейства (у `orig_30072026` и
`image.after.bin` общих 13 записей при разных профилях).

**Вывод для панели: у CSME 15 профиль из дампа не читается.** Ни числом (его в
образе нет), ни длиной таблицы (она говорит о сборке, а не о плате), ни флагами FPF
(они нулевые и там, где CDMD называет профиль 5). Строка панели остаётся «записи о
профиле нет» — и это не пробел в разборе, а свойство формата: уровень Boot Guard
платы живёт на стороне BIOS (манифест политики загрузки, который читает ECFinder),
а не в регионе ME.

## Профиль у CSME 15 всё-таки читается — битами в UEP

**Вывод выше («у CSME 15 профиль из дампа не читается») неверен**, и ошибка была в
поиске, а не в образе: я искал **число** (одно из 0/3/4/5) и байт, который
различает все четыре профиля сразу. Профиля в образе числом и нет — FIT хранит
**четыре настройки, из которых профиль состоит**, и уже из их сочетания выводит
номер. Ни один байт при этом не различает все четыре профиля, поэтому поиск
«значение-метка» и не мог ничего найти.

**Это написано в самих документах FIT.** В `fit-15.0.exe` (zlib-документы внутри
`.exe`) есть классы и действия:

```xml
<Class name="BootGuardProfileSettings">
  <CfgOpt name="FBGAcmEn"               value="false" type="class:BooleanValues"/>  <!-- true=0x1, false=0x0 -->
  <CfgOpt name="VerifiedBoot"           value="false" type="class:BooleanValues"/>
  <CfgOpt name="MeasuredBoot"           value="false" type="class:BooleanValues"/>
  <CfgOpt name="ProtectBiosEnvironment" value="false" type="class:BooleanValues"/>
  <CfgOpt name="ErrorEnforcement_0"     value="0xC"   type="byte"/>
  <CfgOpt name="ErrorEnforcement_1"     value="0xC"   type="byte"/>
</Class>
<Class name="BootGuardProfiles">
  <LayoutEntry name="Boot Guard Profile 0 - No_FVME" value="0" init="FBGAcmEn=false Verified=false Measured=false Protect=false"/>
  <LayoutEntry name="Boot Guard Profile 3 - VM"      value="3" init="FBGAcmEn=false Verified=true  Measured=true  Protect=true "/>
  <LayoutEntry name="Boot Guard Profile 4 - FVE"     value="4" init="FBGAcmEn=true  Verified=true  Measured=false Protect=true "/>
  <LayoutEntry name="Boot Guard Profile 5 - FVME"    value="5" init="FBGAcmEn=true  Verified=true  Measured=true  Protect=true "/>
</Class>
```

Место — класс `Uep` (та самая область `$UEP`): `Signature` dword, `Crc` word,
`Reserved` word, `data` BLOB, а внутри `data` — `IntelArrays` из восьми
`UepBitsArray0…7` по 0x80 байт. Профиль в первой из них, и это записано
действиями (по три адресата на каждую настройку — три копии в трёх массивах):

```xml
<Action name="GetBitArrayValue" source="$BootGuardProfileSettings/FBGAcmEn"
        target="UepBitsArray0" params="{'offset':'0x60','startBit':16,'bitCount':1}"/>
   …  ProtectBiosEnvironment → startBit 19,  MeasuredBoot → 20,  VerifiedBoot → 21
   …  BtGuardCpuDebugEnable → 17,  BtGuardBspInitEnable → 18,  BtGuardKeyManifestId → 22, bitCount 4
```

**Измеренное место в образе.** Байты массива начинаются на **0x0C** от сигнатуры
`$UEP` (в классе этого нет — там `data` идёт сразу за восемью байтами шапки, а в
образе между ними ещё четыре; поэтому место измерено, а не выведено), значит
байт флагов — **`$UEP`+0x6E**, биты: 0 `FBGAcmEn`, 3 `ProtectBiosEnvironment`,
4 `MeasuredBoot`, 5 `VerifiedBoot`. Рядом — другая настройка того же массива
(слово по `$UEP`+0x68), а *достоверность привязки* проверяется тем же байтом:
`BtGuardKeyManifestId` из него (биты 22–25, младшим вперёд) даёт 0x1 — ровно то,
что FIT пишет в своём `.xml` для тех же образов.

**Проверка — по `.xml`, которые сохранил владелец.** Три образа одной сборки,
у которых FIT показывает разные профили, различаются **ровно этим одним полем**
(полный diff `csme15-bg3.xml` / `csme15-bg5.xml`: 16 отличий, из них 15 — пути
`C:\Users\Maksim Shevelev\Desktop\fit-15.0\csme15-bgN\…`, шестнадцатое —
`BtGuardProfileConfig`):

| образ | FIT `.xml` | байт `$UEP`+0x6E | биты (ACM/Prot/Meas/Ver) | наш ответ |
|---|---|---|---|---|
| `1.bin` (плата) | `0 - No_FVME` | 0x40 | 0 0 0 0 | `0 - No_FVME` |
| `csme15-bg0/00.bin` | (сборка профиля 0) | 0x42 | 0 0 0 0 | `0 - No_FVME` |
| `csme15-bg3.bin` | `3 - VM` | 0x7A | 0 1 1 1 | `3 - VM` |
| `csme15-bg4.bin` | (сборка профиля 4) | 0x6B | 1 1 0 1 | `4 - FVE` |
| `csme15-bg5.bin` | `5 - FVME` | 0x7B | 1 1 1 1 | `5 - FVME` |
| `CSME 15.bin` (вход сборок) | — | 0x7B | 1 1 1 1 | `5 - FVME` |
| `2.rom`, `1.bin_S0.bin` (платы) | — | 0x40 | 0 0 0 0 | `0 - No_FVME` |

И то же читается там, где **есть CDMD** — два независимых механизма на одном
образе: `orig_30072026.BIN` (CSME 16.1) — CDMD `5`, биты 0x79 → `5 - FVME`;
`LENV_CSME 16.bin` — CDMD `5`, биты 0x79 → `5`; `Asus/CSME 16.1.bin` — CDMD `0`,
биты 0x00 → `0`.

**Где ответа нет и почему.** У `CSME 12.BIN` и `W25Q256JV.orig.bin` (CSME 12)
контейнер `$UEP` есть, но на месте массива нули (там своя структура — её байты по
+0x28), у `HP EliteBook 630 …G11` (CSME 18) область пустая целиком: все три
отвечают «записи нет», а не «профиль 0». Поэтому чтение ограничено CSME 15 и 16 —
поколениями, на которых оно проверено; вслепую применять его к 12/14/18 нельзя.

**Что осталось непонятным (и не читается).** Два бита в том же байте — `CpuDebug`
(bit 17) и `BspInit` (bit 18) — с показаниями FIT не сходятся: у `1.bin` они 0, а
FIT пишет `Enabled`; у сборок 1 и 0, а FIT пишет `Disabled`/`Enabled`. Значит эти
две настройки FIT берёт не отсюда (или не только отсюда) — их не читаю.
Третья копия флагов видна по `$UEP`+0x1E2 и +0x2EE и всегда равна первой, но
откуда именно берётся 0x0C (смещение массива) и что за поле перед массивом — не
выведено, а измерено.

## MFIT на CSME 16 пишет те же биты — опыт проведён (2026-10-16)

**Вопрос был:** три дампа CSME 16 показывали ту же четвёрку бит, что и CDMD
(`orig_30072026.BIN` — CDMD 5 и 0x79; `LENV_CSME 16.bin` — 5 и 0x79;
`Asus/CSME 16.1.bin` — 0 и 0x00), но это одинаково объяснялось и «MFIT их пишет»,
и «образ унаследовал их из входа, из которого собран проект». Различить могла
только сборка.

**Ответ: пишет.** Три сборки одного входа (вход — образ с CDMD `0` и байтом
`$UEP`+0x6E = `0x00`, то есть у самого входа профиль 0), отличающиеся только
`Boot Guard Profile`:

| сборка | байт `$UEP`+0x6E | биты ACM/Ver/Meas/Prot | наш ответ | индекс в CDMD JSON |
|---|---|---|---|---|
| `csme16-bg0.bin` | 0x00 | 0 0 0 0 | `0 - No_FVME` | 0 |
| `csme16-bg3.bin` | 0x38 | 0 1 1 1 | `3 - VM` | 1 |
| `csme16-bg5.bin` | 0x39 | 1 1 1 1 | `5 - FVME` | 3 |

Биты **сдвинулись** вместе с профилем, а не остались входовыми, — значит их
пишет инструмент, и на 16-й чтение живое. Подтверждено с трёх сторон сразу:
`.xml` самого MFIT (`0 - No_FVME` / `3 - VM` / `5 - FVME`), цифра в JSON CDMD
(0/1/3) и биты. **Биты в байте те же самые**, что у FIT 15 — 0 ACM, 3 protect,
4 measured, 5 verified: `0x38` = три старших без ACM (VM), `0x39` = все четыре
с ACM (FVME). Разметка классов пережила смену инструмента.

**Diff трёх сборок между собой — 13 байт на 16 МБ.** `bg0` против `bg5`: девять
участков, и все осмысленные — CRC области `$UEP` (+0x04), байт флагов (+0x6E) и
его **две копии** (+0x1E2, +0x2EE — так что это действительно копии одного поля,
а не три разных), ещё по одному байту в копиях поля у `FBGAcmEn` (+0x7F, +0x1AB,
+0x21B), плюс в блоке CDMD: длина записи (0x29C012) и её хеш (0x29C016) — и цифра
профиля прямо в тексте JSON (0x29D3DF). Пересборка MFIT **воспроизводима**: у FIT
15 две сборки того же образа расходились на десятки килобайт (страницы MFS
переезжали), здесь же весь образ байт в байт, кроме перечисленного.

**Вход и сборка на его профиль.** `bg0` против входа — 172 участка, 5563 байта,
и все внутри окна 0x290000–0x29FFFF: MFIT переписал блок CDMD и область `$UEP`,
**BIOS-регион не тронул вовсе**. Внутри самой области `$UEP` разница ещё меньше:
CRC и три поля хеша ключа (+0xA0, +0x150, +0x250), которых у входа не было —
он был **без ключа** (нули). Ключ в проект добавил владелец, скопировав его с
ленововских плат: `3BEC6173…` — тот же хеш, что у `1.bin` и `2.rom` (по 9 копий
в каждом), а в сборках его по три. Добавить пришлось потому, что **MFIT не даёт
выставить профиль, отличный от нулевого, при пустом ключе**, — и это не придирка
инструмента: ненулевой профиль означает, что платформа будет сверять BIOS с
ключом OEM, а образу без ключа такое состояние не соответствует. Остальное в
области — байт в байт; то же отношение, что у 15-й (`bg5` == `CSME 15.bin` по
этой области): сборка на профиль входа область не переписывает.

**Что это значит для движка.** Гейт чтения (CSME 15 и 16) подтверждён не
совпадением, а управляемым опытом — сужать его не нужно. И появился факт, которого
раньше не на чем было увидеть: оба места **пишет инструмент при сборке**, поэтому
расхождение CDMD с битами — не «одно из двух врёт», а след того, что образ собран
из частей разных сборок (или одну из записей писал другой инструмент). На всех
дампах под рукой они сходятся, так что строка об этом пока не заведена.

**Чем опыт ещё полезен как приём.** На 16-й различие двух сборок по профилю —
тринадцать байт, то есть diff двух образов даёт ответ сразу и без разбора структур.

## fit-14.0.exe разобран: карта для CSME 14 и где в области лежит профиль

**Карта есть.** `fit_map.py` теперь берёт и 14-ю:
`--straps cml_lp --generation 14 --tool 14.0` (разбор семейства и поколение —
параметры, иначе шапка файла врала бы про 15-ю). Вышло **10 файлов, 31 настройка**.

**Какое семейство у дампа, решил микрокод.** `SPI_EF4018_128Mbit.orig.bin`
(14.0.33.1125, SKU Consumer LP, Lenovo) в BIOS-регионе несёт CPUID `0x806EA`,
`0x806EB`, `0x806EC` (Comet Lake U) и `0xA0660` (Comet Lake S) — значит семейство
`cml_lp`, а не Ice Lake и не Jasper Lake. Проверка чтением дампа через карту:
пять файлов находятся (`mca/eom`, `cfg_rules`, `si_features`, `mctp/smt2_devices`,
`amt/skip_rtfd/ncsi` — те же пять, что и у 15/16), и `EOM = 1` в `mca/eom`
совпадает с тем, что движок читает по этому же файлу независимо (живая запись
`/home/mca/eom = 0x01`).

Отличия семейства от поздних карт: **записи End of Manufacturing нет вовсе**
(FIT 14 связывает `mca/eom` и не связывает `eom_config` — поэтому у 14-й строка
Manufacturing опирается на дескриптор), и есть свои файлы iunit —
`port_cfg`, `sec_ctl`, `sec_touch`, `camera_mask`, которых в 15/16 нет, там вместо
них `iunit_oem_cfg` и `iunit_privacy_mode`.

**Почему раскладки 15-й у 14-й не сработали.** FIT 14 раскладывает те же
четыре бита **по-разному для каждого семейства** — в ресурсах семь разных
раскладок:

| раскладка | первая цель | вторая | третья |
|---|---|---|---|
| док. 38 | `UepBitsArray0` +0x60 бит 16 | `Array2` +0x3c | `Array4` +0x18 |
| док. 39 и 42 | `UepBitsArray0` +0x60 бит 16 | `Array2` +0x3c | `Array3` +0x64 |
| док. 40 | `UepBitsArray0` +0x5c бит 0 | `Array2` +0x48 | `Array4` +0x24 |
| док. 41 и 43 | `UepBitsArray0` +0x44 бит 0 | `Array1` +0x60 | `Array2` +0x70 |
| док. 44 | `UepBitsArray0` +0x30 бит 0 | `Array1` +0x00 | `Array1` +0x48 |

Раскладка «+0x60 бит 16 в массивах 0, 2, 3» — та самая, что подтверждена на 15/16
(там флаги по `$UEP`+0x6E). Какая из семи у `cml_lp`, из exe **не достаётся**: имена
ресурсов лежат в нём не открытым текстом (Qt rcc), а порядок потоков совпадением
имён не подтверждается. Дамп тоже не решает: по всем семи раскладкам первый байт
читается как `0x00`, а это и «профиль 0», и «битов нет».

Отдельно про устройство области у 14-й — она **другая**, чем у 15/16: записи
`0xCC`-политики по +0x20, указатель `80 c0 5a 00` по +0x48, а на месте 48-байтного
хеша — **32 байта высокой энтропии по +0x90 и 16 нулей за ними**, то есть запись
`{SHA-256 + битовая карта}`, та же, что была замечена у 12-й, и не та, что читает
наш движок (он ищет 48 байт по +0xA0).

**Опыт проведён (2026-10-16): профиль у 14-й читается — из записи области, а не из
массивов.** Четыре сборки FIT 14.0.20 одного и того же дампа
(`~/Downloads/1/csme14-bg{0,3,4,5}.bin`; `.xml` отличаются только
`BtGuardProfileConfig`) расходятся **пятью байтами из шестнадцати миллионов**:

| от `$UEP` | bg0 (0) | bg3 (3) | bg4 (4) | bg5 (5) | что это |
|---|---|---|---|---|---|
| +0x04 | 55 09 | 90 a4 | 28 cb | c6 b8 | контрольная сумма контейнера (u16) |
| +0x34 | cc | cc | ff | ff | слово «ACM форсирован» (`0xff`) против «нет» (`0xcc`) |
| +0x4C, +0xE8, +0x178 | 46 | 7e | 6f | 7f | байт флагов — по копии на запись, три записи, всегда равны |

XOR флагов с `0x46` даёт ровно **0x38 / 0x29 / 0x39** — те же три константы, что и
у 15/16 (`ProtectBiosEnvironment` бит 3, `MeasuredBoot` 4, `VerifiedBoot` 5, FBG ACM
0), то есть таблица «сочетание → профиль» здесь та же, а четыре бита лежат в записи
области. Маска по +0x34 подтверждает чтение на одиннадцати дампах и сборках:
`0xff` ровно там, где стоит бит ACM, `0xcc` — где он снят. Она же отличает эту
область от 15/16 (у тех там нули, поэтому 15-я, прочитанная как 12–14, ответа не
даёт) и записанную область от стёртой (у стёртой флаги все единицы, и без маски это
прочиталось бы как профиль 5).

**Что осталось не подтверждённым.** У 13-й дампов нет — она читается по правилу
поколения, как и запись ключа. Профиль 5 у двух образов CSME 12 (Dell Optiplex и
`W25Q256JV.orig.bin` — у обоих в поле ключа `69602f34…`, оба SKU Corporate H) внешним оракулом не сверен: ECFinder под macOS не запускается, нужна
машина с Windows. Четыре образа CSME 12 с нулевым полем ключа читаются как профиль
0 — это согласуется с тем, что FIT не даёт сдвинуть профиль, пока подпись OEM
выключена.

**Косвенное подтверждение найдено (офлайн, 2026-10-16).** У тех же двух образов, что
читаются как 5, BIOS-регион несёт вендорские манифесты Boot Guard — `__KEYM__` и
`__BPM__` по одному разу, — а у четырёх, что читаются как 0, нет ни одного
(`__KEYM__` = 0): чтение флагов совпадает с независимым признаком «BG настроен» на
всех шести. У четырёх сборок CSME 14 BIOS-регионы **побайтово одинаковы**, то есть
изменение профиля до BIOS-стороны не доходит вовсе: в этих сборках настройка живёт
только в записи UEP.

## Ключ OEM у CSME 12–14 читается: 32 байта по `$UEP`+0x90

**Запись другая, чем у 15/16, и её нашли на материале Google Drive.** Движок
раньше читал 48 байт по +0xA0 — у 12/14 это половина хеша и 16 байт битовой
карты за ним, поэтому ответ был «структура не распознана». У 12/14 запись —
**32 байта SHA-256 по +0x90**, за ними 16 байт битов назначения (они **не** часть
хеша), и она встречается в области **один раз**: вторая половина области у этих
поколений на всех образах под рукой стёрта в `FF`.

**На чём проверено.** Пять плат CSME 14 (Acer `ZGEA_104_NO_MM.bin` — без ключа,
нули; Acer `…SRJAU.bin`, Razer `razerrz090368.bin`, Lenovo `Y750 LA-J561P`,
HP `ZBook Studio G7`, Dell `XPS 13 7390`) и шестой образ — вторая копия той же
платы Acer (`CLR ME REGION outimage.bin`), у которой **хеш совпадает с платной
байт в байт** (`65BF2038…`). Ключи разных вендоров различны: Razer `5ACD992C…`,
Lenovo `EAD900A5…`, HP `CF617690…`, Dell `FB6AE279…`.

**Почему запись выбирается по поколению, а не «попробовать обе».** Ошибка в длине
не выглядит мусором: чтение 48 байт у 14-й начинается со второй половины хеша и
уходит в нули карты, чтение 32 байт у 15-й — с нулей перед ключом и захватывает
его первую половину. Оба «неверных» чтения имеют энтропию с одного конца и
паддинг с другого, то есть проходят любую проверку «похоже на хеш». Проверка,
которая это показывает (`me_eom.py`, обе записи на одном образе):

```
=== SPI_EF4018_128Mbit.orig.bin  (CSME 14)
OEM key hash (CSME 12–14, 32 bytes): C19DD2E0116570F84D7B84D7095F90BB02403E869FAF56550A8DBC7F00664940
OEM key hash (CSME 15+, 48 bytes):   02403E869FAF56550A8DBC7F00664940 0000… (вторая половина хеша и нули)
=== 1.bin  (CSME 15)
OEM key hash (CSME 12–14, 32 bytes): 0000…0000 3BEC617351668E9FD97BFC8229CC9F60 (нули и первая половина ключа)
OEM key hash (CSME 15+, 48 bytes):   3BEC617351668E9FD97BFC8229CC9F6064D9D5CD1D284BEEB5F02EE040A1394C33D21714C3652C691418CDC24109BA21
```

Поэтому в движке запись выбирается по `identity.major` (12–14 → короткая, иначе
длинная) — читатель `BootGuardReader.oemPublicKeyHash(in:major:)`.
